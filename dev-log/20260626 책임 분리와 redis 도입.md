### 1. CorsConfig — Setter 바인딩 문제
- 커밋: `9d62cf5` (refactor(config): CORS 설정을 CorsProperties 레코드로 분리)

#### 의문점
- CorsConfig가 빈을 정의하는 일과 yml 값을 바인딩하는 일을 동시에 하고 있었다.
- 바인딩을 `@Setter`로 받고 있었다. `@Setter` 방식은 가변성이 있어 추후 의도치 않은 변경 가능성이 있고 런타임 오류로 진행될 수 있어 권장되지 않는 것으로 알고 있었다.

#### 당시코드
```java
// Before
@Configuration
@ConfigurationProperties(prefix = "app.cors")
@Getter
@Setter
public class CorsConfig {
    private List<String> allowedOrigins; // yml 파일에서 읽음

    @Bean
    public CorsConfigurationSource corsConfigurationSource() {
        CorsConfiguration configuration = new CorsConfiguration();
        configuration.setAllowedOrigins(allowedOrigins);
        ...
    }
}
```

#### 해결법
바인딩 책임을 불변 `record` 로 떼어내고, `CorsConfig`는 생성자 주입을 받는 형식을 택했다.

```java
// After — 설정값은 불변 record로 분리
@ConfigurationProperties(prefix = "app.cors")
public record CorsProperties(List<String> allowedOrigins) {
    public CorsProperties {
        // 누락이면 부팅 시점에 바로 실패시키고, 외부 변경 불가능하게 복사
        allowedOrigins = List.copyOf(Objects.requireNonNull(
                allowedOrigins, "app.cors.allowed-origins must be configured"));
    }
}

// 빈 조립만 담당, 설정은 final로 주입
@Configuration
@RequiredArgsConstructor
public class CorsConfig {
    private final CorsProperties corsProperties;
    ...
}
```
#### 알게 된 것과 변경 후 이점
- 이전 코드 또한 잘못된 것은 아니지만 최근에는 생성자 주입을 더 권장한다고 한다.
- 또한 책임을 나눔으로써 자연스럽게 재사용성이 높아졌다. `CorsProperties`를 `WebSocketConfig`에서도 재사용할 수 있게 되었다.

### 2. 효율적인 이메일 인증 방법
- 커밋: `9295d31` (refactor(auth): 이메일 인증코드·Refresh 토큰을 MySQL에서 Redis로 이전)
- 관련 커밋: `2648279` (이메일 인증 만료 시 미인증 계정 회수)

#### 의문점
- 이메일 인증코드는 3분만 살았다 사라지는 임시 데이터다. 휘발성 데이터를 RDS에 넣는 것이 최선인가? 라는 의문이 들었다.
- 무엇보다 이메일 인증을 끝내지 않은 사람도 실제 회원과 같은 테이블에 들어가 있었다. Type으로 분류는 가능하지만 효율적이지 않단 생각이 들었다.
- 회원가입 시점에서 관련 데이터를 삭제할 수도, 스케줄링으로 제거할 수도 있지만 이것 또한 유지 비용이란 생각이 들었다. 심지어 조회도 아닌 삭제 방식은 비용이 더 큰 것으로 알고 있었다. (소규모 서비스에선 미미하겠지만 서비스가 커질수록 문제가 있다고 생각했다)
- 이를 해결하고자 방안을 찾아보던 중 Redis를 활용할 수 있다고 생각하였다.
- RefreshToken 또한 같은 문제를 안고 있었고 써보지 않은 기술 스택이었기에 도입을 결정하였다.

#### 당시코드
인증 토큰이 `@Entity` 였고, 저장·조회·삭제가 전부 DB I/O로 나갔다.
```java
// Before — 영구 테이블에 매핑된 임시 데이터
@Entity
@Table(name = "email_verification_tokens", indexes = { ... })
public class EmailVerificationToken {
    @Id @GeneratedValue(strategy = IDENTITY)
    private Long id;
    private Long userId;
    private String token;          // 6자리 코드
    private LocalDateTime expiresAt;
    private int failedAttempts;
    private LocalDateTime createdAt;
    ...
}

// JPA 어댑터 — save/delete 가 전부 MySQL 행 조작
@Component
public class EmailVerificationTokenPersistenceAdapter implements ... {
    private final EmailVerificationTokenJpaRepository repository;
    public EmailVerificationToken save(...) { return repository.save(token); }
    public void delete(...) { repository.delete(token); } // 만료돼도 누군가 지워줘야 함
    ...
}
```

#### 해결법
데이터의 성격에 맞는 저장소로 옮겼다. `영속 데이터(회원)는 RDS`, `휘발 데이터(인증코드·Refresh 토큰)는 Redis(TTL)`.

```java
// After — @Entity 떼고 순수 POJO + Redis 복원용 restore() 추가
public class EmailVerificationToken {
    private final Long userId;
    private final String token;
    private final LocalDateTime expiresAt;
    private int failedAttempts;
    public static EmailVerificationToken restore(...) { ... } // Redis 값 → 도메인 복원
}

// After — Redis 해시. 키는 사용자당 1건, TTL 이 청소를 대신한다.
@Component
public class EmailVerificationTokenRedisAdapter implements ... {
    private static final String KEY_PREFIX = "email_verify:"; // email_verify:{userId}
    private static final long GRACE_SECONDS = 60;

    public EmailVerificationToken save(EmailVerificationToken token) {
        String key = key(token.getUserId());
        redis.opsForHash().putAll(key, Map.of("token", ..., "expiresAt", ..., "failedAttempts", ...));
        // 남은 유효시간 + GRACE 만큼만 살린다
        long ttl = Duration.between(now(), token.getExpiresAt()).getSeconds() + GRACE_SECONDS;
        redis.expire(key, Duration.ofSeconds(Math.max(1, ttl)));
        return token;
    }
}
```
- `키 설계`: `email_verify:{userId}` 로 사용자당 1건. 재발송하면 같은 키를 덮어쓰므로 옛 코드가 자동으로 무효화된다(별도 삭제 불필요).
- `GRACE(60초)의 역할`: TTL을 "만료시각까지 남은 시간 + 60초"로 잡았다. 만료 직후 잠깐은 키가 살아있어서 "만료된 코드입니다" 라고 정확히 응답해주고, 그 60초가 지나면 Redis가 알아서 키를 지운다. ->  `만료 토큰 청소 배치`가 통째로 사라졌다.
- 마지막으로 `V30` 마이그레이션으로 `email_verification_tokens`·`refresh_tokens` 테이블을 DROP했다.

#### 알게 된 것과 변경 후 이점
- NoSQL과 RDS에 담기는 분류 기준을 정하자 이 데이터가 휘발성 데이터인지, 영속성 데이터인지 구분할 수 있게 되었다.
- 인증코드·Refresh 같은 휘발 데이터가 RDS에서 빠졌다. 다만 이 시점까지는 인증 안 한 계정을 뒤늦게 정리하는 구조였다 -> 이는 2-2단계에서 완벽히 정리한다.
- `이메일 인증코드` 관련으로 더 이상 MySQL 커넥션과 디스크 I/O를 먹지 않는다. 작은 운영 서버(4GB)에서 MySQL 부담을 덜 수 있었다.
- 만료 토큰 청소용 스케줄러/배치가 아예 필요 없어졌다. (TTL이 인프라 차원에서 대신함)
- 헥사고날 아키텍처의 이점을 체감했다. 포트가 도메인과 인프라를 끊어줬기 때문에, 저장소를 통째로 바꿔도 비즈니스 메인 로직엔 영향이 없었다.


### 2-2. 미인증 계정을 RDS에서 제거하기

#### 의문점
- 1단계로 인증코드는 Redis로 뺐지만, 미인증 User 데이터가 MySQL에 먼저 생기는 구조는 그대로였다.
- 앞서 설명했듯 '실제 서비스를 이용하는 유저'만 RDS에 넣고 싶었다. 즉, RDS를 통해 사후처리를 아예 하고 싶지 않았다.


#### 해결법
- 가입 입력값과 인증코드를 `PendingRegistration` 도메인에 담아 `인증 전까지 Redis에만` 둔다(키 = email, TTL 자동 만료).
- 인증에 성공할 때만 실제 `User`를 RDS에 INSERT한다. -> 미인증 유령 row가 처음부터 생기지 않는다.


#### 당시코드
```
[Before] register() → users INSERT(emailVerified=false)   ← 유령 row 발생
         verify()   → emailVerified = true

[After]  register() → Redis  signup:pending:{email} = {email, 해시비번, 닉네임, code}, TTL 3분
                      (★ MySQL 쓰기 0건)
         verify()   → Redis에서 꺼냄 → users INSERT(인증완료 회원)
                      → 기본아이템 이벤트 발행 → Redis 키 삭제
```
- 흩어져 있던 책임도 한곳에 모였다. 이제 `AuthService.register()`는 비밀번호만 해싱해 `EmailVerificationService.startRegistration()`에 넘기고 끝. 유저 생성·기본아이템 이벤트 발행은 전부 인증 성공 지점(`verifyEmail`)으로 이동했다.


#### 중복 유저 막기 (이메일/닉네임)
기존엔 미인증 User 데이터가 이메일/닉네임 중복 방지 역할을 했고 DB UNIQUE가 최종 방어선이었다. 이제 row가 없으니 이 "소프트 예약"을 Redis 키로 옮겼다.
- `signup:pending:{email}` (해시) = 가입 본문 -> 같은 이메일로 동시 가입을 막음
- `signup:nick:{nickname}` (문자열) = email -> 인증 진행 중인 닉네임 선점을 막음(다른 이메일이 같은 닉을 못 고르게)
- 최종 동시성 문제는 verify 시점의 `DB UNIQUE 제약`이 최종으로 잡는다.


#### 트레이드오프
- 비밀번호가 Redis 대기에만 있으므로, 3분이 지나 대기가 사라지면 재발송할 원본이 없다. 3분이 지나면 재가입 안내를 해야 한다.

#### 알게 된 것과 변경 후 이점
- Redis로 인증 메일을 관리하는 법까지는 들어봤고 실제로 효율적인 방안이라고 생각했지만, 실제 회원만 RDS에 보관하자는 생각을 해보았고 이런 방식이 실제로도 쓰인다는 걸 알게 되었다.
- 실제 회원은 RDS에 보관하여 분류가 편할 뿐만 아니라, 사후처리와 실제 성능에(DB 커넥션과 디스크 I/O)서도 이득을 보았다.

### 3. AsyncConfig의 추상체인 AsyncConfigurer의 메서드들 반환값 문제 
- 기술적 해결이나 성능 개선은 아니지만, Spring 내부 동작 중 몰랐던 부분을 알게 되어 적어본다.

#### 의문점
1) Spring에서 제공하는 `AsyncConfigurer`의 메서드인 `getAsyncExecutor()`와 `getAsyncUncaughtExceptionHandler()`가 default 값으로 `null`을 반환하는 것을 확인했다.
2) 처음에는 `null`을 반환하면 NPE 위험이 있는 게 아닌가? 라는 의문이 들었다.
3) 또한 추상화 목적의 인터페이스라면 구현을 강제하거나 기본 객체를 반환할 것 같은데, 왜 굳이 `null`을 반환하도록 만들어 두었는지 궁금했다.
4) 따라서 `null`을 반환하는 것이 스프링 내부 로직을 돌아가게 하는 일종의 약속이라고 가정하고 이유를 찾아보았다.


#### 해당 코드
```java
public interface AsyncConfigurer {

	/**
	 * The {@link Executor} instance to be used when processing async
	 * method invocations.
	 */
	@Nullable
	default Executor getAsyncExecutor() {
		return null;
	}

	/**
	 * The {@link AsyncUncaughtExceptionHandler} instance to be used
	 * when an exception is thrown during an asynchronous method execution
	 * with {@code void} return type.
	 */
	@Nullable
	default AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
		return null;
	}

}
```

#### 탐색
코드를 따라가 보니, `AsyncConfigurer#getAsyncExecutor()`의 null 반환은 예상대로 Spring 내부에서 의도적으로 처리되는 값이었다.

#### 해당 코드 AsyncExecutionAspectSupport
```java
	public void configure(@Nullable Supplier<Executor> defaultExecutor,
			@Nullable Supplier<AsyncUncaughtExceptionHandler> exceptionHandler) {

		this.defaultExecutor = new SingletonSupplier<>(defaultExecutor, () -> getDefaultExecutor(this.beanFactory));
		this.exceptionHandler = new SingletonSupplier<>(exceptionHandler, SimpleAsyncUncaughtExceptionHandler::new);
	}
```

#### 동작구조
1. `defaultExecutor`가 `null`을 반환하면 `SingletonSupplier`가 fallback supplier인 `getDefaultExecutor(this.beanFactory)`를 호출한다.
2. `AsyncConfigurer#getAsyncExecutor()` 반환값 사용
3. null이면 BeanFactory에서 TaskExecutor 타입 bean 탐색
4. 없으면 이름이 taskExecutor인 Executor bean 탐색
5. 그래도 없으면 `SimpleAsyncTaskExecutor` 생성
- 즉, 사용자가 별도 executor를 제공하지 않았다는 신호가 `null` 반환이었던 것이다.

#### 알게 된 것
- `getAsyncExecutor()`의 기본 구현이 null을 반환하는 이유는 사용자가 별도 executor를 지정하지 않았다는 것을 Spring 내부 로직에 알려주기 위함이다.
- 단순히 `@Async` 설정을 사용하는 것에서 끝나는 것이 아니라, Spring이 어떤 순서로 executor를 결정하고 fallback을 수행하는지 이해할 수 있었다.
- Spring이 Java의 다형성을 적극적으로 활용한다는 말은 알고 있었지만, `AsyncExecutionAspectSupport`의 공통 로직과 `AnnotationAsyncExecutionInterceptor`의 오버라이딩 구조를 보며 이를 실제 코드로 확인할 수 있었다.

2026-07-16

모바일 조이스틱 작업을 마치고 지인 홍보전, 운영 체크를 위해 Grafana에 접속했다가 502에러를 확인했다.

********************************************************************************

### 1. Grafana에만 뜨는 502에러
프론트, 백엔드 헬스체크 등 다른 api나 기능들은 정상작동했다. 그렇다면 grafana가 컨테이너가 죽은것이다.

#### 로그를 보다
```
version=13.1.0  compiled=2026-06-23
restarts=30027  status=restarting

level=error msg="Failed to provision data sources" error="Datasource provisioning error: data source not found"
level=error module=*api.HTTPServer err="failed to start *api.HTTPServer,
  because it depends on module provisioning, which has failed"
```

**재시작 30,027회.** 분당 1회꼴로 3주 넘게 죽고 살아나기를 반복하고 있었다. 실서비스였으면 눈치 못 챌수도없고, 눈치 못 챘다면 상당히 큰 타격이 있었을것이다..

********************************************************************************

### 2. 원인: `:latest`

`docker-compose.prod.yml` 에는 이렇게 적혀 있었다.

```yaml
image: grafana/grafana:latest   # 운영 안정화 시 특정 버전 핀 권장(예: grafana/grafana:11.4.0)
```

grafana의 버전을 최신버전으로만 맞추고 있었다. 초창기에 빠른 배포를 위해 작성한 것을 수정하지 않은것 이었다. 실제 운영에서는 절대 나오면 안되는일이다.. 즉, 초창기 버전과 최신 버전의 충돌로 인해 컨테이너가 죽은것 이었다


#### 왜 데이터소스 하나 때문에 서버 전체가 안 뜨나
이 부분이 이번에 가장 인상 깊었다. 로그를 보면 Grafana는 기능들을 **모듈**로 띄우고, 모듈 간 의존 관계를 선언해 둔다.

```
provisioning (실패)
   ├─ *api.HTTPServer          ← 못 뜸
   ├─ *updatemanager.PluginsService
   ├─ *authz.EmbeddedZanzanaService
   └─ ...
```

`api.HTTPServer` 가 `provisioning` 에 의존하므로, 프로비저닝이 실패하면 **HTTP 서버 자체가 아예 기동하지 않는다.** 그래서 "데이터소스 하나 안 잡히는" 정도가 아니라 포트가 열리지 않았고, Caddy 입장에선 상대가 없으니 502였다.


********************************************************************************

### 3. 눈치채지 못한 이유

Grafana가 죽어 있던 3주 동안, **이메일 알림은 단 한 번도 발송되지 않았다.**

당연한 말인데 당하고 나서야 실감했다. 나는 "에러가 나면 알림이 오겠지"를 전제로 서버를 방치하고 있었고, 그 알림을 보내는 주체가 바로 죽어 있던 Grafana였다. 에러가 실제로 있었는지 없었는지는 이제 알 수도 없다. Loki 보관 기간이 14일이라 초기 로그는 이미 지워졌다.

그래서 이번 일의 교훈은 ":latest 쓰지 말자"를 넘어서 **모니터링 시스템은 그 자체로 감시 대상이어야 한다.** 지금 구조에서는 Grafana가 죽으면 그 사실을 알려줄 수단이 하나도 없다. 외부 감시 시스템을 도입하거나, grafana컨테이너가 죽으면 알려줄 방법이 필요하다.


********************************************************************************

### 4. 왜 3주 동안 몰랐나

원인 자체보다 이쪽이 더 중요한 것 같다.

- **아무것도 안 깨졌다.** 서비스는 멀쩡히 돌았다. Grafana는 사용자 요청 경로에 없으니 죽어도 티가 안 난다.
- **볼 일이 없었다.** 만들어놓고 쓰지 않았다. 대시보드가 0개라 열어도 볼 게 없었으니 열지 않았고, 열지 않으니 죽은 걸 몰랐다.

셋이 겹치면 장애는 조용히 영구화된다. 특히 두 번째가 뼈아프다. **쓰지 않는 인프라는 살아 있는지조차 알 수 없다.** 이번에 대시보드 14패널을 만든 건 기능 추가라기보다, 앞으로 "볼 이유"를 만들어 두는 작업에 가깝다.

### 5. 조치

- 관측 스택 이미지를 **전부 현재 버전으로 고정**했다. `grafana 13.1.0` / `prometheus v3.13.1` / `loki 3.7.3` / `promtail 3.6.8`.
  - Prometheus·Loki·Promtail은 **돌던 버전 그대로** 못 박은 것이라 동작이 바뀌지 않는다. 버전을 올리는 게 아니라 **떠내려가지 않게 고정**하는 게 목적이다.
  - Loki가 특히 위험했다. 메이저가 오르면 `loki-config.yml` 의 `schema_config` 가 호환되지 않아 같은 방식으로 죽는다. 다음 배포에서 터질 수 있었다.
- 알림 수신처를 이메일 전용으로 바꾸었다.
- 로컬(`docker-compose.dev.yml`)에도 같은 버전으로 관측 스택을 올렸다. **로컬에서 확인한 게 운영에서 그대로 동작해야 한다** — 이번 사고의 본질이 결국 "로컬과 운영이 다른 걸 돌리고 있었다" 였다.

프로젝트 전체 버전 관리도 훑어봤다. `:latest` 는 관측 스택 4개뿐이었고, 나머지는 생각보다 괜찮았다.

- `mysql:8.0`, `redis:7-alpine`, `node:20-alpine` 처럼 **메이저만 고정**된 건 그대로 두기로 했다. 패치는 자동으로 받고 호환성은 지켜지는, 의도된 절충이다. `:latest` 와는 위험도가 다르다.
- Gradle은 Spring Boot `3.4.1` + BOM으로 고정, npm은 `package-lock.json` + `npm ci` 라 운영 빌드는 완전히 재현된다. 이건 처음부터 잘 해둔 축이다.

********************************************************************************

### 정리

`:latest` 는 "항상 최신"이 아니라 **"언제 바뀔지 모름"** 이다. 편해 보이는 기본값이 사실은 배포마다 주사위를 굴리는 선택이었다.

이번에 남길 것 세 가지.

1. **버전 고정은 최신을 포기하는 게 아니라, 언제 올릴지를 내가 정하겠다는 선언이다.** 올리지 말자는 게 아니라 릴리스 노트를 보고 의도적으로 올리자는 것이다.
2. **감시 시스템은 스스로를 감시하지 못한다.** 외부에서 봐주는 눈이 하나는 있어야 한다.

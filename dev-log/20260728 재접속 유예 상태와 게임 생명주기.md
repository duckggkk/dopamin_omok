2026-07-28

게임 중 WebSocket 연결이 끊기면 30초 동안 재접속을 기다리고, 한 판에서 최대 두 번까지 기회를 주는 기능을 다시 검토했다.

처음에는 `DisconnectGraceManager`에 `clearState()`가 있으므로 게임이 끝나면 상태가 정리될 것이라고 생각했다. 그러나 호출 경로를 검색해 보니 메서드는 정의만 되어 있고 실제로 호출되는 곳이 없었다. 그 결과 취소된 타이머는 사라져도 연결 끊김 횟수는 다음 판까지 남을 수 있었다.

이번에는 단순히 메서드를 호출하는 데서 끝내지 않고, 유예 상태의 생명주기를 어디에 맞춰야 하는지와 같은 문제가 다시 생기지 않도록 어떤 테스트를 작성해야 하는지 정리했다.


********************************************************************************

### 1. 재접속은 성공했지만 끊김 횟수는 사라지지 않았다

연결이 끊기면 `(roomCode, userId)`를 키로 사용해 횟수를 증가시키고 패배 처리 작업을 예약한다.

```java
int count = counts.computeIfAbsent(key, k -> new AtomicInteger(0))
        .incrementAndGet();

if (count > MAX_CHANCES) {
    runInTransaction(graceAction, roomCode, userId);
    counts.remove(key);
    return;
}

ScheduledFuture<?> future = scheduler.schedule(
        graceAction,
        GRACE_SECONDS,
        TimeUnit.SECONDS
);
timers.put(key, future);
```

사용자가 30초 안에 재접속하면 `cancelGrace()`가 호출된다.

```java
public boolean cancelGrace(String roomCode, Long userId) {
    return cancelTimer(key(roomCode, userId));
}
```

여기서 타이머만 취소하고 `counts`는 지우지 않는 것은 같은 판 안에서는 올바른 동작이다. 재접속할 때 횟수까지 초기화하면 사용자가 연결을 반복해서 끊어도 매번 첫 번째 기회로 처리되기 때문이다.

문제는 한 판이 끝난 뒤에도 `counts`가 그대로 남았다는 점이다.

```text
첫 번째 판
  1회 끊김 → count=1 → 재접속으로 타이머 취소
  2회 끊김 → count=2 → 재접속으로 타이머 취소

리매치 시작
  첫 끊김 → count=3 → 30초 유예 없이 즉시 패배
```

`MAX_CHANCES`의 의미는 “이 방에서 평생 두 번”이 아니라 “한 판에서 두 번”이다. 따라서 `counts`의 생명주기도 방이나 WebSocket 세션이 아니라 한 번의 게임에 맞춰야 했다.

### 2. 정의되어 있다는 것과 실제 흐름에 연결되어 있다는 것은 다르다

기존 코드에는 다음 메서드가 있었다.

```java
public void clearState(String roomCode, Long userId) {
    String key = key(roomCode, userId);
    cancelTimer(key);
    counts.remove(key);
}
```

메서드만 보면 필요한 정리 동작이 이미 구현된 것처럼 보인다. 하지만 전체 호출 경로를 검색하니 이 메서드를 호출하는 코드는 없었다.

이 경우 메서드 단위로만 코드를 읽으면 버그를 발견하기 어렵다. 다음 세 가지를 함께 확인해야 했다.

1. 상태를 만드는 곳은 어디인가?
2. 정상 흐름에서 상태를 소비하거나 취소하는 곳은 어디인가?
3. 상태의 생명주기가 끝날 때 제거하는 호출자가 실제로 존재하는가?

특히 타이머, 캐시, 세션 레지스트리처럼 DB 트랜잭션 밖에 존재하는 인메모리 상태는 엔티티 상태가 바뀐다고 자동으로 정리되지 않는다. `Room`이 `WAITING`으로 돌아가거나 `Game`이 종료돼도 `DisconnectGraceManager`의 두 맵은 이를 알 수 없다.

정리 메서드가 존재하는지만 볼 것이 아니라 생성부터 제거까지의 전체 흐름을 확인해야 한다.

### 3. 사용자 단위 `clearState()`를 방 단위 `clearRoom()`으로 바꾼 이유

새 판이 시작될 때는 어느 한 사용자의 상태만 지우는 것이 아니라 그 방에 속한 모든 참가자의 상태를 초기화해야 한다.

그래서 `(roomCode, userId)` 하나를 받던 `clearState()`를 방 코드 하나만 받는 `clearRoom()`으로 변경했다.

```java
public void clearRoom(String roomCode) {
    String prefix = roomCode + ":";

    timers.keySet().stream()
            .filter(k -> k.startsWith(prefix))
            .toList()
            .forEach(this::cancelTimer);

    counts.keySet().removeIf(k -> k.startsWith(prefix));
}
```

`timers`에서 키를 바로 제거하는 것으로는 충분하지 않다. 맵에서 `ScheduledFuture` 참조만 없애도 스케줄러에 등록된 작업은 계속 실행되기 때문이다. 반드시 `future.cancel(false)`까지 호출해야 한다.

또한 `cancelTimer()`가 내부에서 `timers.remove()`를 실행하므로, 순회 중인 키 집합을 그대로 수정하지 않도록 대상 키를 먼저 `toList()`로 복사했다.

방별 별도 인덱스를 만들 수도 있지만 현재 두 맵의 크기는 전체 회원 수가 아니라 최근 연결이 끊겼거나 유예 중인 사용자 수에 가깝다. 현재 규모에서는 방 코드 접두사로 순회하는 단순한 구현이 별도 인덱스의 동기화 복잡도보다 적합하다고 판단했다.

### 4. 게임 종료가 아니라 새 판 시작 시 초기화한 이유

처음에는 게임이 끝날 때마다 `clearRoom()`을 호출하는 방식을 생각했다. 하지만 게임 종료 경로는 여러 곳에 흩어져 있었다.

- 정상 오목 승리
- 항복
- 시간 초과
- 연결 끊김으로 인한 패배
- 방장 퇴장
- 피지컬 게임 종료 이벤트
- 방 정리 스케줄러

이 모든 경로에 정리 호출을 추가하면 현재는 동작하더라도 새 종료 경로가 생길 때 호출을 빠뜨릴 가능성이 높다.

반면 이전 판의 횟수가 문제가 되는 시점은 다음 판을 시작할 때다. 일반 시작은 `startGame()`, 재대국은 `startRematch()`로 진입점이 제한되어 있다.

```java
disconnectGraceManager.clearRoom(roomCode);
room.startGame();
```

```java
disconnectGraceManager.clearRoom(room.getRoomCode());
room.startGame();
```

이렇게 하면 이전 판이 어떤 경로로 끝났는지와 관계없이 새 판은 항상 깨끗한 유예 상태로 시작한다.

방이 완전히 닫히는 `discardEmptyRoom()`과 `closeRoomByHost()`에서도 `clearRoom()`을 호출했다. 이 경우에는 다음 판의 정합성뿐 아니라 실행할 필요가 없어진 예약 작업과 카운트를 메모리에서 제거한다는 의미도 있다.

이번 수정에서 가장 중요한 판단은 “정리 코드를 어디에 더 많이 넣을 것인가”가 아니라 “상태가 새로 유효해지는 단일 경계가 어디인가”를 찾은 것이다.

### 5. 30초를 기다리지 않는 테스트 구조

기존 `DisconnectGraceManager`는 내부에서 직접 스케줄러를 만들었다.

```java
private final ScheduledExecutorService scheduler =
        Executors.newScheduledThreadPool(4);
```

이 상태에서 공개 동작만으로 테스트하려면 실제로 30초를 기다리거나, 리플렉션으로 비공개 맵을 검사해야 했다. 전자는 테스트가 지나치게 느리고 후자는 구현 세부사항에 강하게 결합된다.

운영에서는 기존처럼 스레드 풀을 생성하되, 테스트에서는 스케줄러를 주입할 수 있도록 생성 경계를 분리했다.

```java
@Autowired
public DisconnectGraceManager(TransactionTemplate transactionTemplate) {
    this(transactionTemplate, Executors.newScheduledThreadPool(4));
}

DisconnectGraceManager(
        TransactionTemplate transactionTemplate,
        ScheduledExecutorService scheduler
) {
    this.transactionTemplate = transactionTemplate;
    this.scheduler = scheduler;
}
```

테스트는 가짜 `ScheduledExecutorService`를 사용하므로 실제 시간이 흐를 필요가 없다. “스케줄 작업이 몇 번 등록됐는가”, “즉시 패배 작업이 실행됐는가”, “어느 타이머가 취소됐는가”를 바로 검증할 수 있다.

스케줄러의 소유권도 명확히 했다. 운영 생성자가 직접 만든 스레드 풀이므로 Spring 빈이 종료될 때 함께 종료한다.

```java
@PreDestroy
void shutdown() {
    scheduler.shutdownNow();
}
```

비동기 자원을 직접 생성하는 객체는 시작뿐 아니라 종료 책임도 가져야 한다.

### 6. 추가한 회귀 테스트

`DisconnectGraceManagerTest`에는 네 가지 동작을 고정했다.

#### 같은 판의 세 번째 연결 끊김은 즉시 처리한다

두 번 끊겼다가 재접속한 후 세 번째로 끊기면 새 타이머를 예약하지 않고 패배 작업을 즉시 실행하는지 확인한다.

이 테스트는 `cancelGrace()`가 같은 판의 횟수까지 지우면 안 된다는 기존 정책을 보호한다.

#### 새 판에서는 첫 연결 끊김에 다시 유예를 부여한다

첫 판에서 두 번의 기회를 사용한 뒤 `clearRoom()`을 호출하고 다시 끊는다. 세 번째 스케줄 작업이 등록되고 패배 작업이 즉시 실행되지 않는지 검증한다.

이 테스트가 이번 버그를 직접 재현하는 핵심 회귀 테스트다.

```java
scheduleAndReconnect(graceAction);
scheduleAndReconnect(graceAction);

manager.clearRoom(ROOM_CODE);
manager.scheduleGrace(ROOM_CODE, USER_ID, graceAction);

verify(scheduler, times(3)).schedule(...);
verify(graceAction, never()).run();
```

#### 해당 방의 모든 타이머만 취소한다

한 방의 두 사용자와 다른 방의 사용자에게 각각 타이머를 등록한다. `clearRoom()` 호출 후 대상 방의 두 타이머만 취소되고 다른 방 타이머는 유지되는지 확인한다.

이 테스트는 방 단위 정리와 방 사이의 격리를 함께 검증한다.

#### 빈 종료 시 스케줄러를 종료한다

`shutdown()`이 `scheduler.shutdownNow()`를 호출하는지 확인한다. 애플리케이션 재시작이나 테스트 컨텍스트 종료 후 스레드가 남지 않도록 자원 종료 책임을 고정한다.

실행 명령은 다음과 같다.

```powershell
.\gradlew.bat test --tests "com.dopamin.omok.global.websocket.DisconnectGraceManagerTest"
```

작성한 네 테스트는 모두 통과했다.

### 7. 이번 테스트가 보장하지 않는 범위

이번 테스트는 실제 브라우저가 STOMP로 연결하고 끊기는 전체 흐름을 띄우는 통합 테스트가 아니다. `SessionDisconnectEvent` 이후 호출되는 유예 상태 컴포넌트의 정책을 검증하는 단위 테스트다.

따라서 다음 항목은 별도의 검증이 필요하다.

- `SessionDisconnectEvent`와 재구독 이벤트가 매우 짧은 간격으로 동시에 처리되는 경우
- `scheduleGrace()`와 `clearRoom()`이 정확히 동시에 실행되는 경쟁 조건
- 실제 STOMP 재연결 후 `cancelGrace()`까지 이어지는 통합 흐름
- 서버가 여러 인스턴스로 확장됐을 때 인메모리 타이머와 카운트의 공유

현재 구조는 `ConcurrentHashMap`으로 개별 맵 연산의 안전성은 확보하지만, 여러 맵과 스케줄러 등록을 합친 전체 동작이 하나의 원자적 연산이 되는 것은 아니다.

이번 수정은 정상적인 게임 상태 전환에서 이전 판의 상태가 다음 판으로 넘어가는 문제를 막는다. 이를 모든 WebSocket 동시성 문제를 해결한 것으로 확대해서 해석하면 안 된다.

### 정리

1. 재접속 시 타이머는 취소되지만 같은 판의 끊김 횟수는 유지되어야 한다.
2. 문제는 그 횟수가 다음 판까지 유지된다는 것이었다.
3. 기존 `clearState()`는 구현만 있고 실제 호출자가 없었다.
4. 유예 횟수의 생명주기는 방이 아니라 한 판에 맞춰야 한다.
5. 종료 경로마다 정리하기보다 `startGame()`과 `startRematch()`에서 방 상태를 초기화했다.
6. `clearRoom()`은 맵 항목뿐 아니라 예약된 `ScheduledFuture`도 취소해야 한다.
7. 스케줄러를 주입할 수 있게 만들어 실제 30초를 기다리지 않는 회귀 테스트를 작성했다.
8. 직접 생성한 스케줄러는 `@PreDestroy`에서 종료하도록 소유권을 명확히 했다.
9. 단위 테스트는 정상 상태 전환을 보장하지만 실제 STOMP 통합 흐름과 극단적인 동시 실행은 별도 과제다.

이번 문제는 코드가 없어서 생긴 것이 아니라, 존재하는 정리 코드가 상태 전환 흐름에 연결되지 않아 생겼다. 인메모리 상태를 다룰 때는 저장 자료구조만 볼 것이 아니라 그 상태가 언제 태어나고, 언제까지 유효하며, 어떤 단일 경계에서 반드시 제거되는지를 함께 설계해야 한다.

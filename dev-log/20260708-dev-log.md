### 1. JWT 인증 principal을 `CustomUserDetails`에서 `AuthUser`로 분리

#### 문제점
- 기존 JWT 인증 흐름은 `JwtAuthenticator`에서 access token을 검증한 뒤 `CustomUserDetailsService.loadUserById(userId)`를 호출했다.
- 이 구조에서는 Bearer token이 붙은 HTTP 요청마다 `User` 테이블을 한 번 조회하게 된다.
- 또한 `CustomUserDetails`가 `User` 엔티티 전체를 들고 있었기 때문에, 실제 요청 처리에 필요한 값은 대부분 `id`뿐인데도 password hash, tokenVersion 등 인증 이후에는 불필요한 정보까지 `SecurityContext`의 principal에 남아 있었다.

기존 구조는 보안적으로 완전히 틀린 방식은 아니었다. DB의 현재 `tokenVersion`과 JWT의 `tokenVersion`을 비교하면 새 로그인 이후 이전 access token을 즉시 거부할 수 있다. 하지만 그만큼 JWT의 stateless 장점은 줄어들고, 인증 단계가 DB 부하와 직접 연결된다.

#### 고민한 지점
실무에서 access token을 어떻게 처리하는지 다시 정리했다.

- 일반적인 JWT 기반 API 서버는 access token을 짧게 두고, 매 요청에서는 서명/만료만 검증하는 경우가 많다.
- refresh token은 Redis나 DB에 저장해서 폐기 가능하게 관리한다.
- access token까지 즉시 무효화해야 하는 경우에는 DB 조회보다는 Redis 기반 `tokenVersion` 또는 `jti` blacklist를 두는 편이 더 적합하다.
- 방 참가 여부, 아이템 소유 여부, 프로필 접근 권한 같은 비즈니스 권한은 어차피 서비스 로직에서 DB로 다시 검증한다.

이 프로젝트에서도 대부분의 컨트롤러는 `@AuthenticationPrincipal`에서 `userId`만 꺼내 서비스로 넘기고, 실제 권한 검증은 서비스 레이어에서 수행하고 있었다. 그래서 JWT 인증 단계에서 매번 `User` 엔티티 전체를 조회하는 구조는 과하다고 판단했다.

#### 변경한 방향
JWT 인증 이후 `SecurityContext`에 넣는 principal을 별도 record로 분리했다.

```java
public record AuthUser(
        Long id,
        UUID publicId,
        String email,
        String nickname,
        UserRole role
) {
    public Collection<? extends GrantedAuthority> getAuthorities() {
        return List.of(new SimpleGrantedAuthority("ROLE_" + role.name()));
    }

    public boolean isGuest() {
        return role == UserRole.GUEST;
    }
}
```

핵심은 `AuthUser`가 `UserDetails`를 구현하지 않고, password도 들지 않는다는 점이다. `UsernamePasswordAuthenticationToken`의 principal은 `Object` 타입이므로 record를 넣어도 된다. `@AuthenticationPrincipal`은 `UserDetails` 구현 여부가 아니라 `Authentication.getPrincipal()`에 들어 있는 객체 타입을 기준으로 값을 주입한다.

따라서 컨트롤러는 다음처럼 바뀌었다.

```java
public ResponseEntity<ApiResponse<List<FriendResponse>>> getFriends(
        @AuthenticationPrincipal AuthUser me) {
    return ResponseEntity.ok(ApiResponse.success(friendUseCase.getFriends(me.id())));
}
```

#### JWT claim 기반 인증으로 변경
기존에는 token에서 `userId`, `tokenVersion`을 꺼낸 뒤 DB의 현재 `tokenVersion`과 비교했다.

변경 후에는 token 자체의 서명/만료를 검증하고, claim에서 필요한 사용자 정보를 꺼내 `AuthUser`를 만든다.

```java
AuthUser authUser = new AuthUser(
        jwtProvider.extractUserId(token),
        jwtProvider.extractPublicId(token),
        jwtProvider.extractEmail(token),
        jwtProvider.extractNickName(token),
        jwtProvider.extractRole(token));

return Optional.of(new UsernamePasswordAuthenticationToken(
        authUser, null, authUser.getAuthorities()));
```

이 과정에서 `CustomUserDetails`와 `CustomUserDetailsService`는 제거했다. 현재 로그인은 Spring Security의 username/password 기본 인증을 쓰지 않고 `AuthService`에서 직접 `passwordEncoder.matches(...)`로 검증하기 때문에, JWT 인증용으로 `UserDetailsService`를 유지할 이유가 없어졌다.

#### 추가 문제 광장 세션
단순히 `id`, `email`, `role`만 넣으면 대부분의 HTTP API는 동작한다. 하지만 `PlazaWebSocketController`는 기존에 principal의 `User`에서 `publicId`, `nickname`, `isGuest()`를 꺼내 광장 세션에 사용하고 있었다.

DB 조회를 없앤 상태에서도 같은 기능을 유지하려면 access token에 최소한 다음 값이 필요했다.

- 내부 식별자: `id`
- 외부 노출 식별자: `publicId`
- 표시 이름: `nickname`
- 권한/게스트 판단: `role`

그래서 `JwtProvider.generateAccessToken(...)`이 `UUID publicId`, `UserRole role`을 받도록 바꾸고, JWT claim에는 `publicId`, `email`, `nickName`, `role`, `tokenVersion`을 넣도록 정리했다. Java 내부에서는 `UserRole` enum으로 다루고, JWT 안에는 문자열로 저장한다.

#### tokenVersion의 의미 변화
이 변경에서 가장 중요한 트레이드오프는 `tokenVersion`이다.

기존 구조에서는 다음 비교가 있었다.

```java
JWT tokenVersion == DB users.tokenVersion
```

이 비교가 있었기 때문에 새 로그인으로 `users.tokenVersion`이 증가하면 이전 access token을 즉시 거부할 수 있었다.

하지만 DB 조회를 제거하면서 이 비교도 사라졌다. 따라서 현재 access token 안의 `tokenVersion` claim은 남아 있지만, 인증 정책상 즉시 무효화에는 사용되지 않는다. 즉, 새 로그인 이후에도 기존 access token은 만료 전까지는 통과할 수 있다.

이 선택은 의도적인 트레이드오프다.

- 장점: 요청마다 `users` 조회를 하지 않아 인증 경로가 가벼워진다.
- 장점: `SecurityContext`에 password hash나 `User` 엔티티 전체를 남기지 않는다.
- 단점: access token 즉시 무효화 기능은 사라진다.
- 단점: 기존에 발급된 access token에는 `publicId` claim이 없으므로 재로그인이 필요하다.

즉시 무효화가 다시 필요해지면 DB 조회를 되돌리기보다는 Redis 기반 `tokenVersion` 또는 `jti` blacklist로 옮기는 것이 더 낫다. 또는 access token 만료 시간을 더 짧게 가져가고, refresh token만 서버 상태로 관리하는 방식도 가능하다.

#### 같이 바꾼 부분
- HTTP 컨트롤러의 `@AuthenticationPrincipal CustomUserDetails`를 전부 `AuthUser`로 변경했다.
- WebSocket/STOMP 쪽 `JwtChannelInterceptor`, `WebSocketEventListener`, 게임/피지컬/광장 WebSocket 컨트롤러도 `AuthUser` principal을 읽도록 변경했다.
- `JwtProviderTest`, `JwtAuthenticatorTest`를 새 claim 기반 인증 구조에 맞게 수정했다.


#### 정리
이번 변경은 단순한 타입 교체가 아니라, JWT 인증의 책임을 다시 정리한 작업이었다.

기존 구조는 "JWT를 검증한 뒤 DB에서 현재 사용자를 다시 조회한다"에 가까웠고, 변경 후 구조는 "JWT 자체를 검증하고, token claim으로 최소 principal을 구성한다"에 가깝다.

실무적으로는 이 방향이 더 흔한 JWT API 서버 구조에 가깝다. 다만 access token 즉시 무효화를 포기한 만큼, 운영 단계에서는 access token 만료 시간과 refresh token 폐기 정책을 함께 봐야 한다.

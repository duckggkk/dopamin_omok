### 1. 친구 목록 상대 전적 조회 쿼리 최적화

#### 문제점
친구 목록 API는 단순히 친구의 프로필만 내려주는 것이 아니라, 각 친구와의 상대 전적까지 함께 내려준다.

기존 구조에서는 `FriendService.getFriends(meId)`가 친구 목록을 조회한 뒤, 친구 한 명마다 `loadHeadToHeadPort.between(meId, otherId)`를 호출했다. 그런데 `HeadToHeadPersistenceAdapter.between(...)` 내부에서는 승/패/무를 각각 따로 세기 위해 `count` 쿼리를 3번 실행하고 있었다.

즉 친구 수가 N명일 때 상대 전적 조회만으로 다음과 같은 쿼리 수가 발생했다.

```text
친구 1명  -> count query 3개
친구 30명 -> count query 90개
친구 100명 -> count query 300개
```

또한 `Friendship`의 `requester`, `addressee`가 lazy 연관관계였기 때문에 친구 목록을 응답 DTO로 바꾸는 과정에서도 사용자 엔티티 조회가 추가로 발생할 수 있었다. 친구 수가 적을 때는 크게 티가 나지 않지만, 친구가 많아질수록 친구 목록 API 하나가 DB에 과도하게 많은 요청을 보내는 구조였다.

처음에는 상대 전적 요약 테이블을 따로 만드는 방법도 생각했다. 하지만 요약 테이블은 조회는 빠르게 만들 수 있어도, 대국 종료 시점마다 쓰기 경로를 수정해야 하고, 기존 데이터 backfill, 동시성 정합성, 장애 시 복구 로직까지 따라온다. 아직 실제 운영 데이터에서 병목이 검증된 상황은 아니었기 때문에, 먼저 조회 쿼리 구조 자체를 개선하는 쪽이 더 적절하다고 판단했다.

#### 변경한 방향
핵심은 친구별로 승/패/무를 따로 세지 않고, 친구 ID 목록 전체를 한 번에 받아 `GROUP BY`로 집계하는 것이다.

`LoadHeadToHeadPort`에 batch 조회 메서드를 추가했다.

```java
Map<Long, HeadToHead> betweenMany(Long meId, Collection<Long> otherIds);
```

그리고 `HeadToHeadPersistenceAdapter`에서 QueryDSL `CaseBuilder`와 `sum()`을 사용해 승/패/무를 한 번의 쿼리로 계산하도록 바꿨다.

- `winner.id == meId`이면 승리
- `winner.id != meId`이고 `winner`가 있으면 패배
- `status == DRAW`이면 무승부

처음에는 상대 ID를 계산하는 `CASE` 식 하나만 기준으로 `GROUP BY`하려고 했다. 하지만 H2가 이 형태의 group by를 엄격하게 처리하면서 테스트에서 문제가 생겼다. 그래서 DB 호환성을 위해 `blackPlayer.id`, `whitePlayer.id` 조합으로 먼저 그룹화하고, 같은 상대가 흑/백 위치를 바꿔 등장한 결과는 Java에서 merge하도록 정리했다.

이 방식은 H2와 MySQL 양쪽에서 동일한 정합성을 유지하면서도, 친구 수와 무관하게 상대 전적 집계 쿼리를 1개로 고정할 수 있다.

`FriendService.getFriends(...)`도 다음 흐름으로 바꿨다.

1. 수락된 친구 관계를 한 번 조회한다.
2. 친구 사용자 ID 목록을 만든다.
3. `betweenMany(meId, friendIds)`로 상대 전적을 한 번에 집계한다.
4. 친구 DTO를 만들 때 map에서 전적을 꺼낸다.

추가로 `FriendshipJpaRepository.findInvolving(...)`에는 `JOIN FETCH f.requester`, `JOIN FETCH f.addressee`를 적용했다. 친구 목록을 만들 때 필요한 양쪽 사용자 정보를 한 번에 가져오기 위해서다.

#### 검증
단순히 "쿼리를 줄였다"로 끝내지 않고, 결과 정합성과 쿼리 수를 테스트로 확인했다.

H2 자동 테스트에서는 다음을 검증했다.

- `betweenMany` 결과가 기존 단건 조회 결과와 같은지
- 대국이 없는 친구는 빈 전적으로 처리되는지
- 친구 100명의 상대 전적 batch 조회가 prepared statement 1개로 끝나는지
- 친구 목록 100명 조회 전체가 prepared statement 2개로 끝나는지

H2만으로는 실제 MySQL 실행 시간을 판단하기 어렵기 때문에, 로컬 MySQL 별도 DB에서도 벤치마크를 돌렸다. 벤치마크 DB는 `dopamin_omok_bench`로 분리했고, `ddl-auto=create-drop`으로 테스트 실행마다 스키마를 새로 만들도록 했다.

측정 조건은 친구 1명당 5승, 3패, 2무를 seed하고, 실제 games 테이블에 더 가까운 조건을 만들기 위해 친구 수의 10배만큼 무관한 종료 대국을 추가했다.

| 친구 수 | 기존 3-count 반복 방식 | Batch 집계 | 현재 FriendService 경로 |
| ---: | ---: | ---: | ---: |
| 1 | 184 ms / 3 queries | 244 ms / 1 query | 40 ms / 2 queries |
| 30 | 47 ms / 90 queries | 14 ms / 1 query | 13 ms / 2 queries |
| 100 | 157 ms / 300 queries | 8 ms / 1 query | 22 ms / 2 queries |

친구 1명일 때 batch 집계가 더 느리게 나온 것은 연결, 캐시, 실행 계획 같은 일회성 비용과 측정 오차의 영향을 받기 쉽다. 중요한 지점은 친구 수가 늘어날 때 기존 방식은 쿼리 수가 `3N`으로 증가하지만, batch 방식은 집계 쿼리 1개로 고정된다는 점이다. 30명과 100명 구간에서는 MySQL 측정에서도 batch 방식이 명확하게 유리했다.

#### 요약 테이블을 만들지 않은 이유
이번에는 상대 전적 요약 테이블을 만들지 않았다.

요약 테이블은 읽기 성능만 보면 매력적이다. 하지만 대국이 끝나는 모든 경로에서 요약 row를 갱신해야 한다. 정상 종료, 기권, 무승부, 향후 재처리나 운영자 보정까지 고려하면 쓰기 경로가 복잡해진다. 기존 games 데이터로 요약 테이블을 다시 만드는 backfill도 필요하고, 집계 데이터가 실제 games 테이블과 어긋났을 때 복구할 기준도 필요하다.

현재 측정에서는 친구 100명 기준으로도 batch 집계만으로 충분히 빠르고, 친구 목록 전체 조회도 2개 쿼리로 끝난다. 따라서 지금 단계에서는 요약 테이블을 도입하는 것보다 batch 집계와 적절한 인덱스 확인이 더 현실적인 선택이다.

#### 남은 점검
다음 단계는 games 테이블 인덱스를 확인하는 것이다.

현재 조건은 `(black_player_id = me and white_player_id in friends) OR (white_player_id = me and black_player_id in friends)` 형태다. 데이터가 더 커지면 MySQL이 이 조건을 어떤 실행 계획으로 처리하는지 확인해야 한다.

우선 확인할 인덱스 후보는 다음과 같다.

- `(black_player_id, white_player_id)`
- `(white_player_id, black_player_id)`
- winner/status 조건이 실제 병목에 영향을 주는지 여부

만약 실제 운영 데이터에서 p95/p99 지연이 커지거나 games 테이블 크기가 훨씬 커져 batch 집계만으로 부족해지면, 그때 요약 테이블을 다시 검토하는 것이 맞다. 그 전까지는 쿼리 수를 상수로 줄인 현재 방식이 복잡도 대비 효과가 가장 좋다.

#### 정리
이번 작업은 캐시나 비정규화 테이블을 먼저 도입한 것이 아니라, 기존 조회 로직의 쿼리 구조를 먼저 바로잡은 작업이다.

친구 한 명마다 `count` 3번을 반복하던 구조를, 친구 목록 전체에 대한 batch 집계로 바꿨다. 그리고 H2 테스트로 정합성과 쿼리 수를 검증하고, 로컬 MySQL 벤치마크로 실제 실행 시간도 확인했다.

성능 최적화는 "빠를 것 같다"는 추측보다, 먼저 쿼리 수가 어떻게 증가하는지 확인하고, 변경 후에도 결과가 같은지 검증하는 것이 중요하다는 점을 다시 확인한 작업이었다.

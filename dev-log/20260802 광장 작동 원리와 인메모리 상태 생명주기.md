2026-08-02

만남의 광장은 여러 사용자가 같은 공간에서 캐릭터를 움직이고 채팅하는 실시간 기능이다. 처음에는 WebSocket으로 좌표를 주고받으면 되는 비교적 단순한 기능이라고 생각했다. 그러나 실제로 구현해 보니 채널 배정, 입장 전 구독, 이동 입력과 서버 틱, 연결 종료, 빈 채널 정리까지 하나의 생명주기로 이어져 있었다.

특히 REST로 채널만 배정받고 WebSocket 입장까지 도달하지 않은 경우 빈 채널이 계속 남는 문제를 검토하면서, 광장의 상태가 언제 만들어지고 언제 제거되는지를 다시 정리하게 되었다.

이번 글에서는 화면 기능보다 서버가 광장 상태를 어떻게 소유하고 동기화하는지, 여러 WebSocket 스레드와 틱 스레드 사이의 동시성을 어떻게 처리했는지를 중심으로 정리한다.


********************************************************************************

### 1. 광장은 좌표를 전달하는 기능이 아니라 서버가 공간 상태를 소유하는 기능이다

클라이언트끼리 자신의 좌표를 직접 주고받게 하면 구현은 단순해 보인다. 하지만 이 방식에서는 사용자가 임의 좌표를 보내 순간 이동하거나, 이동 속도를 바꾸거나, 존재하지 않는 채널에 플레이어를 만드는 것을 막기 어렵다.

현재 광장에서는 서버가 다음 상태를 소유한다.

- 존재하는 채널
- 채널별 참가자
- 플레이어의 좌표와 방향
- 이동 중인지 여부
- 현재 외형
- WebSocket 세션과 광장 참가자의 관계

클라이언트는 좌표를 보내지 않고 이동 의도만 보낸다.

```text
MOVE_START + UP
MOVE_START + LEFT
MOVE_STOP
```

서버는 일정한 틱마다 이동 중인 플레이어의 좌표를 직접 계산하고, 계산 결과를 전체 스냅샷으로 전송한다. 클라이언트는 서버 스냅샷을 기준으로 화면만 부드럽게 보간한다.

```text
클라이언트: 위로 이동을 시작하겠다
    ↓
서버: moving=true, facing=UP
    ↓
서버 틱: y = y - moveStep
    ↓
서버: 채널 전체 스냅샷 발행
    ↓
클라이언트: 이전 좌표와 새 좌표 사이를 보간해 렌더링
```

따라서 브라우저에 보이는 좌표는 표현 상태이고, `PlazaSessionManager` 안의 좌표가 권위 상태다.

### 2. 전체 입장 흐름은 REST와 WebSocket의 두 단계로 나뉜다

광장 페이지에 들어갔다고 곧바로 WebSocket의 플레이어가 되는 것은 아니다. 현재 입장 순서는 다음과 같다.

```text
PlazaPage 마운트
    ↓
POST /api/plaza/join
    ↓
PlazaSessionManager.allocate()
    ↓
channelId, 월드 크기, 정원 응답
    ↓
STOMP CONNECT (Access Token 인증)
    ↓
/topic/plaza/{channelId} 구독
/topic/plaza/{channelId}/chat 구독
    ↓
SEND /app/plaza/{channelId}/join
    ↓
PlazaSessionManager.join()
    ↓
플레이어 생성 후 첫 스냅샷 브로드캐스트
```

REST의 `allocate()`는 입장할 채널만 고른다. 실제 플레이어 생성은 WebSocket의 `join()`에서 수행한다.

이렇게 분리한 이유는 클라이언트가 먼저 채널 ID와 월드 정보를 알아야 해당 토픽을 구독할 수 있기 때문이다. 또한 토픽을 먼저 구독한 다음 `join`을 보내므로, 입장 직후 서버가 발행하는 첫 스냅샷을 놓치지 않는다.

하지만 두 단계 사이에는 실패 구간이 생긴다.

```text
allocate 성공
    ↓
페이지 새로고침 또는 네트워크 오류
    ↓
WebSocket join 미실행
```

이 경우 채널은 만들어졌지만 플레이어는 한 명도 없는 상태가 된다. 이 상태를 별도로 정리하지 않으면 `leave`나 disconnect가 발생할 참가자 자체가 없으므로 빈 채널이 계속 남는다.

### 3. 광장의 인메모리 상태 구성

광장 상태는 MySQL이나 Redis가 아니라 백엔드 프로세스 메모리에 있다.

```java
private final ConcurrentHashMap<String, Channel> channels = new ConcurrentHashMap<>();
private final ConcurrentHashMap<String, Member> sessionIndex = new ConcurrentHashMap<>();
private final AtomicInteger channelCounter = new AtomicInteger(0);
private final Object allocationLock = new Object();
```

각 자료구조의 책임은 다르다.

#### `channels`

`channelId → Channel`의 정방향 인덱스다. 채널을 찾고 입력이나 틱을 적용할 때 사용한다.

#### `Channel.players`

한 채널에 입장한 플레이어들을 `userId → PlazaPlayer`로 보관한다. `LinkedHashMap` 자체는 스레드 안전하지 않으므로 반드시 해당 채널의 `ReentrantLock` 안에서 접근한다.

```java
private static final class Channel {
    final String id;
    final long createdAtMs = System.currentTimeMillis();
    final ReentrantLock lock = new ReentrantLock();
    final Map<Long, PlazaPlayer> players = new LinkedHashMap<>();
    boolean movedLastTick = false;
}
```

#### `sessionIndex`

`sessionId → (channelId, userId)`의 역방향 인덱스다. WebSocket disconnect 이벤트에는 STOMP 세션 ID만 들어오므로, 어느 채널에서 어떤 사용자를 제거해야 하는지 찾기 위해 필요하다.

#### `channelCounter`

`plaza-1`, `plaza-2` 형식의 채널 ID를 발급한다. 현재 프로세스 안에서만 증가하며 서버가 재시작되면 다시 0부터 시작한다.

#### `allocationLock`

채널을 선택하고 새 채널을 만드는 동작, 빈 채널을 제거하는 동작을 직렬화한다. 채널 내부 상태를 보호하는 `Channel.lock`과는 보호 범위가 다르다.

`ConcurrentHashMap`을 사용했다고 해서 그 안에 들어 있는 `Channel`과 `PlazaPlayer`까지 자동으로 스레드 안전해지는 것은 아니다. 맵의 조회·삽입·제거와 맵 값 내부의 가변 상태는 별개의 동시성 문제다.

### 4. 채널 배정과 실제 입장에서 검증을 두 번 하는 이유

`allocate()`는 정원이 남은 채널을 먼저 찾고, 없다면 새 채널을 생성한다.

```java
synchronized (allocationLock) {
    for (Channel c : channels.values()) {
        c.lock.lock();
        try {
            if (c.players.size() < props.channelCapacity()) {
                channelId = c.id;
                break;
            }
        } finally {
            c.lock.unlock();
        }
    }

    if (channelId == null) {
        channelId = "plaza-" + channelCounter.incrementAndGet();
        channels.putIfAbsent(channelId, new Channel(channelId));
    }
}
```

그러나 `allocate()`는 자리를 예약하지 않는다. 채널에 29명이 있을 때 여러 사용자가 REST 배정을 연속으로 요청하면 모두 같은 채널 ID를 받을 수 있다. 실제 인원은 아직 `join()` 전이라 29명으로 보이기 때문이다.

따라서 정원 검사는 `join()`에서도 다시 수행해야 한다.

```java
if (!c.players.containsKey(userId)
        && c.players.size() >= props.channelCapacity()) {
    return;
}
```

이 검사는 전형적인 TOCTOU 문제를 막는다. 배정 시점에 확인한 조건이 실제 입장 시점에도 그대로라는 보장은 없다.

`join()`은 그 밖에도 다음 순서로 방어한다.

1. `allocate()`가 만든 채널이 실제로 존재하는지 확인한다.
2. 같은 WebSocket 세션이 다른 채널에 남아 있으면 기존 채널에서 먼저 제거한다.
3. 채널 락을 기다리는 동안 빈 채널 정리가 실행됐을 수 있으므로 `channels.get(channelId) == c`인지 다시 확인한다.
4. 실제 입장 시점의 정원을 다시 확인한다.
5. 월드 경계 안의 임의 좌표에 플레이어를 생성한다.
6. `sessionIndex`를 등록하고 첫 스냅샷을 발행한다.

예전처럼 `join()`에서 `computeIfAbsent`로 채널을 만들면 클라이언트가 임의의 채널 ID를 보내 서버 메모리에 채널을 무한히 생성할 수 있다. 그래서 채널 생성 권한은 REST `allocate()`에만 두고, WebSocket `join()`은 이미 발급된 채널만 사용한다.

현재 남은 한계도 있다. 배정 이후 실제 입장 전에 정원이 차면 `join()`은 조용히 거부되지만, 클라이언트에 재배정을 요구하는 오류 응답은 아직 없다. 정원 경쟁이 실제로 발생할 정도로 사용자가 늘면 사용자 전용 오류 큐나 재배정 흐름이 필요하다.

### 5. 입력 스레드와 틱 스레드는 채널 락으로 직렬화한다

WebSocket 입력은 여러 클라이언트 스레드에서 동시에 들어올 수 있다. 반면 이동 틱은 하나의 스케줄러 스레드가 실행한다.

```java
scheduler = Executors.newSingleThreadScheduledExecutor(...);
scheduler.scheduleAtFixedRate(
        this::tickSafely,
        interval,
        interval,
        TimeUnit.MILLISECONDS
);
```

틱이 단일 스레드라는 사실만으로 동시성 문제가 사라지는 것은 아니다. 틱이 `PlazaPlayer`의 좌표를 변경하는 순간 다른 WebSocket 스레드가 이동 방향을 바꾸거나, 참가자를 제거하거나, 외형을 바꿀 수 있다.

그래서 다음 동작들은 모두 채널별 `ReentrantLock` 안에서 실행한다.

- 입장과 퇴장
- 이동 시작과 정지
- 외형 변경
- 멤버십 검사
- 틱 이동 계산
- 스냅샷 생성

채널별로 락을 나눴기 때문에 `plaza-1`에서 입력을 처리하는 동안 `plaza-2`까지 같이 멈추지는 않는다.

서버는 플레이어가 이동 중이면 틱마다 다음 계산을 수행한다.

```java
player.step(moveStep, worldWidth, worldHeight);
```

`PlazaPlayer.step()`은 현재 방향의 `dx`, `dy`에 틱당 이동량을 곱해 좌표를 변경하고 월드 경계 안으로 clamp한다. 기본 설정은 100ms마다 12px이므로 초당 약 120px을 이동한다.

클라이언트가 임의 좌표나 이동 거리를 보내지 않기 때문에 이동 속도와 월드 경계는 서버 설정으로 일관되게 유지된다.

### 6. 두 종류의 락과 잠금 순서

현재 광장에는 두 종류의 락이 있다.

```text
allocationLock
  채널 선택·생성·제거 보호

Channel.lock
  한 채널 내부의 players와 플레이어 상태 보호
```

`allocate()`와 `cleanupIfEmpty()`는 다음 순서로 락을 획득한다.

```text
allocationLock → Channel.lock
```

그런데 틱은 이미 `Channel.lock`을 잡은 상태다. 이 안에서 곧바로 `cleanupIfEmpty()`를 부르면 잠금 순서가 반대가 된다.

```text
틱:       Channel.lock → allocationLock 대기
allocate: allocationLock → Channel.lock 대기
```

두 스레드가 서로 상대 락을 기다리면 데드락이 발생한다. 이를 피하기 위해 틱에서는 제거할 빈 채널을 목록에만 모은다.

```java
List<Channel> staleChannels = null;

for (Channel c : channels.values()) {
    c.lock.lock();
    try {
        if (정리_대상) staleChannels.add(c);
    } finally {
        c.lock.unlock();
    }
}

for (Channel c : staleChannels) {
    cleanupIfEmpty(c);
}
```

모든 채널 락을 놓은 뒤 `cleanupIfEmpty()`를 호출하므로 잠금 순서가 한 방향으로 유지된다.

이번 구현을 통해 락이 필요한 위치뿐 아니라 여러 락을 어떤 순서로 잡는지도 설계의 일부라는 점을 다시 확인했다. 각각의 코드 블록만 보면 안전해 보여도, 전체 호출 경로에서 잠금 순서가 뒤집히면 교착 상태가 생길 수 있다.

### 7. 매 틱 전체 스냅샷을 보내되 완전히 멈추면 전송하지 않는다

현재 광장은 좌표 변화량만 보내는 델타 방식이 아니라 채널 전체 상태를 스냅샷으로 보낸다.

```java
public record PlazaSnapshot(
        String channelId,
        int worldWidth,
        int worldHeight,
        List<PlazaPlayerView> players,
        long serverTime
) {}
```

전체 스냅샷은 메시지 크기가 더 크지만 다음 장점이 있다.

- 중간 프레임 하나를 놓쳐도 다음 스냅샷만 받으면 상태가 복구된다.
- 클라이언트가 입장 직후 별도의 과거 이벤트를 재생할 필요가 없다.
- 서버와 클라이언트 사이의 상태 불일치를 찾기 쉽다.
- 채널 정원이 30명인 현재 규모에서는 구조가 단순하다.

반면 아무도 움직이지 않는데 100ms마다 같은 스냅샷을 보내는 것은 낭비다. 이를 줄이기 위해 `movedLastTick`을 사용한다.

```java
if (moving || c.movedLastTick) {
    broadcast(c);
}
c.movedLastTick = moving;
```

누군가 움직이는 동안에는 매 틱 전송한다. 모두 멈춘 첫 틱에는 마지막 정지 위치를 한 번 더 보낸다. 그다음부터는 완전히 정지한 채널의 전송을 생략한다.

입장, 퇴장, 외형 변경은 틱을 기다리지 않고 즉시 스냅샷을 발행하므로 정지 상태에서도 화면 갱신이 누락되지 않는다.

프론트는 서버의 100ms 스냅샷 사이를 `requestAnimationFrame`으로 렌더링하며 현재 표시 좌표를 목표 좌표 쪽으로 보간한다.

```typescript
rp.x += (p.x - rp.x) * 0.25;
rp.y += (p.y - rp.y) * 0.25;
```

서버 틱을 무작정 60fps로 올리지 않고, 서버는 비교적 낮은 빈도로 권위 상태를 제공하고 브라우저가 시각적 부드러움을 담당하도록 역할을 나눴다.

### 8. 명시적 퇴장과 비정상 연결 종료를 모두 처리해야 한다

정상적으로 페이지를 나가면 클라이언트는 다음 메시지를 보낸다.

```text
SEND /app/plaza/{channelId}/leave
```

그러나 브라우저 종료, 네트워크 단절, 프로세스 종료에서는 이 메시지가 전달된다고 보장할 수 없다. 그래서 `SessionDisconnectEvent`에서도 세션 ID를 이용해 퇴장을 처리한다.

```java
public void handleDisconnect(String sessionId) {
    Member member = sessionIndex.remove(sessionId);
    if (member == null) return;
    leave(member.channelId(), member.userId());
}
```

`leave()`는 채널의 플레이어를 제거하고 남은 참가자에게 새 스냅샷을 보낸다. 마지막 플레이어가 나가면 `cleanupIfEmpty()`가 채널 자체를 제거한다.

```text
sessionIndex로 disconnect 역추적
    ↓
players에서 사용자 제거
    ↓
퇴장 반영 스냅샷 발행
    ↓
players가 비었으면 channels에서도 제거
```

정상 퇴장과 disconnect를 둘 다 두는 이유는 둘 중 하나만 신뢰할 수 없기 때문이다. 정상 메시지는 빠르게 의도를 전달하지만 전달 보장이 없고, disconnect 이벤트는 비정상 종료를 처리하지만 세션과 도메인 사용자의 관계를 별도 인덱스로 기억해야 한다.

### 9. `allocate()`만 실행된 좀비 채널의 생명주기

플레이어가 한 번이라도 입장한 채널은 마지막 퇴장에서 정리된다. 반면 REST 배정 직후 WebSocket 연결에 실패한 채널은 `sessionIndex`도, 플레이어도 없어서 기존 퇴장 흐름으로 정리할 수 없었다.

이를 위해 채널에 생성 시각을 기록했다.

```java
final long createdAtMs = System.currentTimeMillis();
```

틱은 플레이어가 없고 생성 후 `joinTimeoutMs`가 지난 채널을 좀비 채널로 판단한다.

```java
if (c.players.isEmpty()
        && now - c.createdAtMs >= props.joinTimeoutMs()) {
    staleChannels.add(c);
}
```

기본 제한 시간은 30초다. 방금 배정되어 WebSocket 연결을 준비 중인 정상 채널은 바로 제거하지 않고, 플레이어가 실제로 입장한 채널은 생성된 지 오래됐더라도 제거하지 않는다.

이번 문제에서 중요한 점은 “빈 채널이면 삭제한다”가 아니었다. `allocate()`와 `join()` 사이에는 정상적인 빈 상태가 존재하므로, 상태가 비었다는 조건에 시간 조건을 더해 아직 입장을 기다리는 채널과 영원히 입장하지 않을 채널을 구분해야 했다.

### 10. 채팅과 외형도 서버의 신뢰 경계를 통과한다

광장 STOMP 연결은 CONNECT에서 Access Token을 검증한다. 클라이언트가 `/app/plaza/{channelId}/chat`으로 채팅을 보내면 컨트롤러는 실제 채널 멤버인지 다시 확인한다.

닉네임은 요청 본문에서 받지 않고 인증된 `AuthUser`에서 가져온다.

```java
if (user == null || !manager.isMember(channelId, user.id())) return;

String nickname = user.nickname();
```

따라서 클라이언트가 다른 닉네임을 본문에 넣어 사칭할 수 없다. 채팅 내용은 DTO 검증을 통과한 뒤 `/topic/plaza/{channelId}/chat`으로 발행한다.

일반 스냅샷은 내부 DB 사용자 ID 대신 외부 공개용 `publicId`를 내려준다. 프론트는 이 값으로 자신의 캐릭터를 찾고, 다른 캐릭터를 클릭했을 때 공개 프로필로 이동한다.

외형에는 아직 남은 경계가 있다. 게스트의 외형 변경은 서버가 차단하지만, 회원이 요청한 헤어·의상 키가 실제 보유 아이템인지까지는 확인하지 않는다. 현재 Phase 1에서는 화면용 키를 그대로 중계하며, 이후에는 `user_active_items`의 서버 권위 장착 상태에서 외형을 만들도록 변경할 예정이다.

또한 클라이언트가 `/topic/**`으로 직접 이벤트를 발행하지 못하도록 `JwtChannelInterceptor`에서 구독과 전송 권한을 분리했다. 컨트롤러의 멤버십과 DTO 검증은 메시지가 `/app/**` 경로로 들어올 때만 의미가 있으므로, 브로커 목적지 직접 전송을 막는 것도 같은 신뢰 경계의 일부다.

### 11. 포트로 분리한 브로드캐스트

`PlazaSessionManager`는 `SimpMessagingTemplate`을 직접 알지 않고 `PlazaEventPublisherPort`에 의존한다.

```text
PlazaWebSocketController
    ↓ 입력
PlazaSessionManager
    ↓ PlazaEventPublisherPort
PlazaWebSocketPublisherAdapter
    ↓
SimpMessagingTemplate
    ↓
/topic/plaza/{channelId}
```

세션 매니저는 광장 상태와 틱 규칙에 집중하고, STOMP 목적지와 메시지 전송 구현은 아웃바운드 어댑터가 담당한다.

현재는 Spring의 인메모리 SimpleBroker를 사용하지만 외부 브로커나 다른 전송 방식으로 바꿀 때 세션 매니저의 도메인 흐름까지 함께 수정하지 않아도 된다. 또한 세션 매니저 단위 테스트에서는 실제 WebSocket 브로커 대신 `PlazaEventPublisherPort`를 mock으로 주입할 수 있다.

### 12. 추가한 좀비 채널 회귀 테스트

`PlazaSessionManagerTest`에는 다음 세 가지 경계를 고정했다.

#### 배정만 되고 입장하지 않은 채널은 제한 시간 이후 제거된다

`joinTimeoutMs`를 1ms로 두고 채널을 배정한 뒤 틱을 직접 실행한다. 플레이어가 없는 채널이 제거되는지 확인한다.

#### 아직 입장을 기다리는 채널은 유지된다

기본값에 가까운 30초 제한 시간을 사용하고 배정 직후 틱을 실행한다. 정상적인 REST와 WebSocket 사이 구간을 좀비로 오판하지 않는지 확인한다.

#### 플레이어가 있는 채널은 오래돼도 제거하지 않는다

제한 시간을 지난 뒤에도 실제 플레이어가 들어온 채널은 유지되는지 확인한다.

이 테스트들은 스케줄러를 실제로 시작하지 않고 `tickSafely()`를 직접 호출한다. 따라서 광장 틱의 주기를 기다리지 않으면서 채널 생명주기 정책을 검증할 수 있다.

다만 현재 테스트는 실제 STOMP 연결과 disconnect 이벤트까지 포함하는 통합 테스트가 아니다. 또한 동시에 여러 사용자가 배정·입장·퇴장하는 경쟁 조건과 잠금 순서까지 자동으로 검증하지는 않는다.

### 13. 현재 구조의 한계와 다음 과제

#### 서버 재시작

광장 좌표와 채널은 모두 메모리 상태이므로 서버가 재시작되면 사라진다. 광장은 전적이나 재화처럼 보존해야 하는 업무 데이터가 아니므로 현재는 사용자가 다시 입장하고 새 위치에서 시작하는 정책을 선택했다.

#### 다중 인스턴스

백엔드가 두 대가 되면 각 서버가 자신만의 `plaza-1`과 플레이어 목록을 갖는다. 한 인스턴스가 발행한 SimpleBroker 메시지를 다른 인스턴스에 연결된 사용자가 받지 못할 수도 있다.

Sticky session만으로는 서버 장애와 재접속 문제까지 해결할 수 없다. 확장 시에는 최소한 다음 항목이 필요하다.

- 채널 소유 인스턴스 정보 공유
- 동일 채널 입력을 소유 인스턴스로 라우팅
- 외부 STOMP 브로커 또는 Pub/Sub
- 장애 시 채널을 종료하거나 다른 인스턴스가 인계하는 정책

모든 좌표를 Redis에 매 틱 저장하는 방식은 가능하지만, 네트워크 I/O와 직렬화 비용을 늘린다. 현재처럼 한 인스턴스가 한 채널의 실시간 상태를 소유하고 외부에는 소유권과 이벤트만 공유하는 방식도 검토할 수 있다.

#### 같은 사용자의 여러 세션

현재 `players`는 `userId`를 키로 사용한다. 같은 사용자가 같은 채널을 여러 탭에서 열면 마지막 입장이 플레이어 상태를 덮어쓰지만 각 WebSocket 세션은 `sessionIndex`에 남을 수 있다. 이전 탭이 끊길 때 새 탭의 플레이어까지 제거될 가능성이 있으므로, 다중 탭을 허용할지 한 세션만 유지할지 정책을 명확히 해야 한다.

#### 스냅샷과 락 유지 시간

현재는 일관된 스냅샷을 만들기 위해 채널 락 안에서 브로드캐스트까지 호출한다. 정원 30명과 현재 트래픽에서는 단순하고 안전하지만, 전송 큐가 느려지면 해당 채널 입력도 오래 기다릴 수 있다.

규모가 커지면 락 안에서 불변 스냅샷만 만든 뒤 락 밖에서 발행하거나, 전체 스냅샷과 델타 이벤트를 섞는 방식을 검토해야 한다.

#### 관측 가능성

현재는 입장·퇴장·좀비 채널 정리를 로그로 확인한다. 운영 규모가 커지면 활성 채널 수, 전체 광장 인원, 틱 처리 시간, 초당 스냅샷 수, 입장 거부 수를 메트릭으로 수집해야 병목과 비정상 상태를 더 빨리 발견할 수 있다.

### 정리

1. 광장 클라이언트는 좌표가 아니라 이동 의도만 보내며, 좌표는 서버 틱이 계산한다.
2. 입장은 REST 채널 배정과 WebSocket 실제 입장의 두 단계로 이루어진다.
3. 토픽을 먼저 구독한 뒤 입장해야 첫 스냅샷을 놓치지 않는다.
4. `ConcurrentHashMap`은 채널 맵 연산만 보호하며, 채널 내부 가변 상태는 `ReentrantLock`으로 보호한다.
5. 채널 선택·생성·제거는 `allocationLock`, 채널 내부 상태는 `Channel.lock`이 담당한다.
6. 여러 락을 사용할 때는 `allocationLock → Channel.lock`의 잠금 순서를 유지해야 한다.
7. 틱에서는 채널 락을 놓은 뒤 빈 채널을 제거해 반대 순서 잠금으로 인한 데드락을 피한다.
8. 전체 스냅샷은 메시지 손실 후 복구가 단순하고, `movedLastTick`으로 정지 중 중복 전송을 줄인다.
9. 정상 퇴장 메시지만 믿지 않고 `sessionIndex`와 disconnect 이벤트로 비정상 종료도 정리한다.
10. REST 배정 후 WebSocket 입장이 오지 않은 빈 채널은 `joinTimeoutMs` 이후 좀비 채널로 정리한다.
11. 채팅 닉네임과 이동 좌표는 서버 권위로 관리하지만, 회원 외형의 아이템 소유권 검증은 아직 남은 과제다.
12. 현재 인메모리 구조는 단일 서버와 작은 채널에 적합하며, 다중 서버 전환 시 채널 소유권과 외부 메시지 브로커가 필요하다.

광장을 구현하면서 실시간 기능의 핵심은 메시지를 빠르게 보내는 것만이 아니라는 점을 알게 되었다. 상태를 누가 소유하는지, 어떤 입력을 신뢰할지, 상태가 언제 생성되고 제거되는지, 동시에 실행되는 코드가 어떤 순서로 락을 잡는지를 함께 결정해야 했다.

특히 이번 좀비 채널 문제는 정상적인 입장과 퇴장만 따라가서는 발견하기 어려웠다. 여러 단계로 나뉜 흐름에서는 각 단계 사이에서 사용자가 이탈했을 때 어떤 중간 상태가 남는지도 생명주기의 일부로 봐야 한다.

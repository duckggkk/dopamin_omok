오늘은 기술적 회고나 코드 수정보다 클로드 코드의 도메인 정의를 보면서 도메인의 분리에 대한 회고를 줄글로 남겨본다.


#### 도메인객체란?
개발에서 도메인은 소프트웨어가 해결하려는 업무 또는 문제 영역을 의미한다. 오목 프로젝트에서는 대국 진행, 착수 규칙, 승패 판정 등이 도메인에 해당한다. `도메인 객체`는 이러한 영역의 개념과 규칙을 코드로 표현하고, 자신에게 주어진 책임을 수행하는 객체라고 설명할 수 있다.


#### 도메인과 엔티티
나는 이전 프로젝트 `아이세이`에서 도메인객체 = 엔티티 = DB테이블로 생각하고 관리하였고 엔티티가 아닌 도메인을 생각하기 어려워했다. 물론 그 프로젝트에서도 도메인 역할을하던 클래스들은 존재했지만 `도메인 객체`라고 인식하지 못하고 단순히 `기능이 있는 객체`라고만 생각하였다.


#### 왜 도메인으로 인식하지 못했을까?
첫 번째 이유는 엔티티를 데이터베이스 테이블과 강하게 연결해서 생각했기 때문이다. 영속성 객체에 복잡한 로직을 넣는 것을 부담스럽게 느꼈고, 엔티티에는 간단한 필드 상태 변경 정도만 맡겼다.
두 번째 이유는 비즈니스 책임을 충분히 분리하지 못했기 때문이다. 대부분의 로직을 엔티티 단위의 서비스에 배치하면서 서비스 레이어가 조회, 검증, 계산, 상태 변경, 저장 과정을 순서대로 수행하게 됐다. 복잡해진 서비스를 정리하기 위해 Helper, Utils, Validator 등의 클래스를 만들었지만, 이들을 독립적인 도메인 개념으로 설계하기보다 서비스나 엔티티를 보조하는 객체로만 바라봤다. 


#### 클로드가 작성한 RenjuRuleEngine을 보다
현 프로젝트의 렌주룰 구현은 클로드에 맡겼다. 이유는 세가지인데 첫째로 기존에 명확한 규칙이 존재해 참고할 데이터가 많다. 둘째로 결과를 테스트하기도 비교적 쉽다. 셋째로 생성된 코드를 직접 검토하고 테스트 하는게 훨씬 생산적이라 판단해 클로드에 초안 작성을 맡겼다. 이 과정에서 만들어진 클래스가 `RenjuRuleEngine`이었다. 코드를 보자마자 엔티티가 아니더라도 충분히 도메인 객체가 될 수 있다는 사실을 명확하게 이해할 수 있었다.
`RenjuRuleEngine`은 렌주룰이라는 구체적인 도메인 개념을 표현하고, 착수 가능 여부를 판정하는 명확한 책임을 가지고 있었다. 또한 데이터베이스나 외부 시스템에 의존하지 않아 규칙 자체를 독립적으로 테스트할 수 있었다. 


#### 이전이었다면?
`GameValidator` 하나를 만들고 외부에서 전달받은 `GameType`에 따라 여러 규칙을 조건문으로 분기했을 가능성이 크다. 하지만 현재는 렌주룰이라는 독립적인 변경 이유와 책임을 별도 객체로 분리할 수 있다는 점을 이해하게 됐다.


#### 객체지향의 책임
이전 프로젝트 역시 클래스와 객체를 사용했다는 점에서는 객체지향 코드라고 할 수 있다. 하지만 엔티티는 데이터와 단순 상태 변경만 담당했고, 대부분의 비즈니스 규칙은 서비스와 보조 클래스에 흩어져 있었다. 결과적으로 도메인 모델이 빈약하고 서비스의 책임이 비대해졌다. 이번 프로젝트를 통해 객체지향은 단순히 클래스를 나누는 것이 아니라, 비즈니스 개념을 발견하고 그 개념에 적절한 책임을 부여하는 과정이라는 점을 깨달았다. 

앞으로는 무조건 클래스를 잘게 나누기보다 각 객체가 하나의 응집된 책임과 명확한 변경 이유를 갖는지 고민하려 한다. 어떤 개념을 엔티티로 표현할지뿐만 아니라 값 객체, 도메인 서비스, 규칙 또는 정책 객체로 분리할지도 함께 판단해야 한다.

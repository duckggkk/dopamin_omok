### 1. `SecurityConfig`에 등록하지 않은 `TraceIdFilter`가 보안 필터보다 먼저 실행되는 이유

#### 의문점
`SecurityConfig`를 보면 `JwtAuthenticationFilter`는 다음처럼 Spring Security 필터 체인에 명시적으로 추가되어 있다.

```java
.addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)
```

반면 `TraceIdFilter`는 `SecurityConfig` 어디에도 등록되어 있지 않다. 그런데 TraceIdFilter는 Spring Security필터보다 먼저 작동하며 필터체인에 등록하는듯한 어노테이션도 보이지 않는다.

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class TraceIdFilter extends OncePerRequestFilter {
}
```

#### 탐구 방법
`TraceIdFilter`에서 `@Component`는 스프링빈 등록 어노테이션, `@Order`는 체인순서, 그렇다면 남는 것은 `OncePerRequestFilter`밖에 없다. 이것이 필터 등록의 이유라 가정하고 클래스를 뜯어보았다. (이름부터 Filter가 들어가는게 사실상 확정이라 생각했다)
`OncePerRequestFilter`는 HTTP 요청이 올때 메서드를 구현할 수 있는 클래스로만 얕게 알고있었다. 이번 기회에 `OncePerRequestFilter`의 역할과 서블릿 필터에 등록되는 구조를 알아보고자 한다.


#### 헷갈렸던점
먼저 HTTP요청 시 흐름과 서블릿 필터와 시큐리티 필터의 관계를 알아보야한다.
HTTP요청 -> 프록시 서버 -> 톰캣 서버 -> 서블릿 필터(Spring Security 포함) -> 디스패처 서블릿(해당하는 Controller 배정) -> 컨트롤러 .... 의 형태로 진행된다.

처음에 헷갈린 부분이 이 부분이다. TraceIdFilter가 `Spring Security`안쪽에서 돌거라 생각한 것이다. `SecurityConfig`에 등록이 안 되어있으니 당연한것 이지만 서블릿필터의 이해가 부족하여 서블릿 필터에 `Spring Security`만 있다고 생각한 것이다. 그것이 아니라 서블릿 필터에서 `TraceIdFilter` -> `Spring Security Filter` 순서로 진행된 것이다. (순서는 `Order 어노테이션` 및 `addFilterBefore`으로 지정)


#### `SecurityConfig`의 동작 구조는?
- `SecurityConfig`는 단순히 `SecurityFilterChain`을 정의 및 빈등록을하는 클래스이다.
- `@EnableWebSecurity`은 프로젝트의 모든 `SecurityFilterChain`을 `FilterChainProxy`로 만드는 어노테이션이었다.
- `@EnableMethodSecurity`은 매서드에 `@PreAuthorize`등의 어노테이션을 걸 수 있게 하는 기능이었다.
- `Configuration`과  `RequiredArgsConstructor`은 알고있듯 빈등록과 생성자 등록 어노테션이다. 

즉, 여기에도 서블릿 필터로 등록하는 기능은 존재하지 않았다. 다만 `JwtAuthenticationFilter`가 `TraceIdFilter`와 마찬가지로 `OncePerRequestFilter`를 상속 받았다.


#### OncePerRequestFilter의 역할
`OncePerRequestFilter` -> `GenericFilterBean` -> `Filter`(인터페이스)를 거친다. OncePerRequestFilter는 단순히 ServletRequest,ServletResponse기반 필터 행동과 상태 확인 정도의 코드만 보일뿐, 역시 필터 등록을 하는 코드는 보이지 않았다.


#### 그렇다면 서블릿 필터 등록은 어떻게 하는건가?
답은 간단했다. 스프링 내부 로직으로 Filter를 구현한 빈들을 서블릿 필터로 등록한다. (단, Spring Security의 경우 EnableWebSecurity으로 인해 SecurityFilterChain를 기준으로 하나의 필터로 등록)

서버가 켜질 때 등록되는 순서
ServletWebServerApplicationContext.selfInitialize(ServletContext)
   └─ 부팅 중 "임베디드 톰캣 초기화" 시점
        │
        ▼
ServletContextInitializerBeans          ← 컨텍스트의 모든 빈을 훑어 Filter 타입을 선정
        │                                   
        ▼
FilterRegistrationBean 으로 감쌈          ← 골라낸 Filter를 매핑(URL=/*, 순서=@Order 값 세팅)
        │                                   
        ▼
AbstractFilterRegistrationBean.onStartup(servletContext)
        │
        ▼
servletContext.addFilter(name, filter)  ← 등록


#### 정리
이번 의문은 필터등록 코드가 보이지 않아서 시작했다.

실제 동작은 다음 순서다.

1. `@Component`가 `TraceIdFilter`와 `JwtAuthenticationFilter`를 스프링 빈으로 만든다.
2. 단, `SecurityConfig`가 `@EnableWebSecurity`로 `SecurityFilterChain`를 하나의 서블릿 필터로 묶어준다.
3. `ServletContextInitializerBeans`가 Filter의 구현체를 서블릿 컨테이너에 등록한다.
4. @Order로 서블릿 필터 체인에서 각 필터의 실행 순서를 잡아준다

스프링 코드와 동작구조를 보면은 느껴지는것이 있다. 추상화와 구현의 엄격한 분리, 이로인한 다형성의 활용, 그리고 무엇보다 책임 분리가 명확하게 되어있다. 
이번에만 봐도 각 클래스와 어노테이션의 책임이 명확하게 분리되어 있었다. 이번 탐구로 인해 스프링의 동작구조는 물론이고 JAVA 문법 활용도 많은 도움이 될 것이다.

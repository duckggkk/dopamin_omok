### 1. 전적 목록에 실시간 게임 DTO를 사용하고 있었다

`GameHistoryController`의 내 전적 조회 API는 기존에 `GameResponse`를 반환하고 있었다.

```java
@GetMapping("/games/my")
public ResponseEntity<ApiResponse<Page<GameResponse>>> getMyGames(...) {
    Page<GameResponse> response = getMyGamesUseCase.getMyGames(userDetails.id(), pageable);
    return ResponseEntity.ok(ApiResponse.success(response));
}
```

`GameResponse`는 실시간 대국 상태를 전달하기 위해 만든 DTO다. 현재 차례, 마지막 착수 시각, 승자가 장착한 패배 문구와 이펙트처럼 진행 중인 게임이나 종료 연출에서 필요한 값을 가지고 있다.

문제는 전적 목록에서는 이 값들을 사용하지 않는다는 점이다. 홈과 프로필의 전적 목록에서 필요한 것은 대국 종류, 랭크 여부, 흑·백 플레이어, 승자, 시작 및 종료 시각 정도였다. 그런데 같은 DTO를 재사용하면서 목록에 필요하지 않은 실시간 게임 정보까지 함께 내려가고 있었다.

플레이어 응답도 과했다. `GameResponse`의 흑, 백, 승자는 모두 `PublicUserResponse`였고 여기에는 전체 승·패·무, 모드별 전적, 레이팅, 칭호, 프로필 공개 여부, 가입 시각까지 포함된다.

전적 목록에서 실제로 사용하는 값은 공개 ID와 닉네임 정도이며, 프로필 이미지를 표시하더라도 세 필드면 충분하다. 승자는 흑 또는 백 중 한 명이므로 같은 사용자 정보가 한 번 더 중복되기도 했다.

보안상 비밀번호나 이메일 같은 민감 정보가 노출된 것은 아니었다. 하지만 공개 가능한 정보라고 해서 모든 API가 항상 전부 내려줄 필요는 없다. 필요한 범위보다 많은 응답은 API의 의도를 흐리고, 프론트가 사용하지 않는 필드까지 계약으로 유지하게 만든다.

### 2. 목록 전용 `GameSummaryResponse` 사용

공개 프로필의 전적 목록에서는 이미 `GameSummaryResponse`를 사용하고 있었다. 이 DTO는 플레이어 정보를 `PlayerSummary`로 줄이고, 목록과 다시보기에 필요한 대국 정보만 담는다.

```java
public record PlayerSummary(
        UUID id,
        String nickname,
        String profileImageUrl
) {
}
```

내 전적과 다른 사용자의 공개 전적은 조회 권한을 확인하는 과정은 다르지만, 화면에 표시하는 결과의 형태는 같다. 따라서 `/games/my`도 동일한 요약 DTO를 사용하도록 변경했다.

```java
@GetMapping("/games/my")
public ResponseEntity<ApiResponse<Page<GameSummaryResponse>>> getMyGames(...) {
    Page<GameSummaryResponse> response =
            getMyGamesUseCase.getMyGames(userDetails.id(), pageable);
    return ResponseEntity.ok(ApiResponse.success(response));
}
```

유스케이스와 서비스의 반환 타입도 함께 변경했다.

```java
Page<GameSummaryResponse> getMyGames(Long userId, Pageable pageable);
```

```java
public Page<GameSummaryResponse> getMyGames(Long userId, Pageable pageable) {
    return loadGamePort.findCompletedByUserId(userId, pageable)
            .map(GameSummaryResponse::from);
}
```

컨트롤러에서만 DTO를 바꾸고 서비스가 계속 `GameResponse`를 반환하게 둘 수도 있었다. 하지만 그렇게 하면 애플리케이션 계층이 불필요하게 큰 응답을 만든 뒤 컨트롤러에서 다시 변환해야 한다. 조회 유스케이스가 처음부터 자신이 제공할 응답 형태를 명확히 반환하도록 변경하는 편이 자연스러웠다.

프론트에서도 `GameInfo`와 `GameSummary`를 구분했다.

- `GameInfo`는 현재 방과 실시간 게임 상태에서 사용한다.
- `GameSummary`는 홈 및 프로필 전적 목록과 다시보기 진입에 사용한다.

두 타입을 분리하자 전적 화면이 `currentTurn`, `lastMoveAt`, `winnerDefeatEffect` 같은 실시간 필드에 의존하지 않는다는 사실이 타입으로 드러났다. 서버 DTO와 프론트 타입을 함께 수정하면서 실제 API 계약도 일치시켰다.

### 3. 착수 DTO에서 반복되는 값 제거

전적 조회를 확인하면서 `GameMoveResponse`도 함께 살펴봤다. 한 대국의 착수 목록은 수백 개가 될 수 있고, 실시간 대국 중에도 매 착수마다 같은 DTO가 전달된다.

기존 응답에는 다음 값이 포함되어 있었다.

```java
Long id,
String roomCode,
UUID playerId,
String playerNickname,
StoneColor color,
Integer row,
Integer col,
Integer moveNumber,
String soundAssetKey,
LocalDateTime createdAt
```

하지만 현재 프론트에서 방 코드는 이미 URL과 WebSocket 구독 경로를 통해 알고 있다. 플레이어 UUID도 착수 표시에는 사용하지 않고, 목록의 식별자는 한 판 안에서 유일한 `moveNumber`로 충분했다. 생성 시각 역시 기보 재생에서 사용하지 않았다.

따라서 착수 표현에 실제 필요한 값만 남겼다.

```java
public record GameMoveResponse(
        String playerNickname,
        StoneColor color,
        Integer row,
        Integer col,
        Integer moveNumber,
        String soundAssetKey
) {
}
```

전적 목록 한 건에서 필드 몇 개를 줄이는 것보다 착수처럼 반복 횟수가 많은 응답에서 불필요한 값을 제거하는 효과가 더 클 수 있다. 다만 이번에는 변경 전후의 바이트 크기나 응답 시간을 따로 측정하지 않았으므로 성능이 크게 개선됐다고 단정할 수는 없다. 확실한 변화는 클라이언트가 사용하지 않는 값과 중복 값을 API 계약에서 제거했다는 점이다.

### 4. DTO를 공용으로 만들수록 재사용성이 높아지는가

처음에는 같은 `Game` 엔티티를 기반으로 한다면 `GameResponse` 하나를 여러 API에서 재사용하는 것이 단순하다고 생각할 수 있다. DTO 개수가 줄고 변환 코드도 한 곳에 모이기 때문이다.

하지만 실시간 게임 조회와 전적 목록은 목적이 다르다.

```text
실시간 게임
 ├─ 현재 차례
 ├─ 마지막 착수 시각
 ├─ 종료 연출
 └─ 플레이어의 게임 화면용 정보

전적 목록
 ├─ 대국 종류와 랭크 여부
 ├─ 흑·백 플레이어 요약
 ├─ 승패 결과
 └─ 시작 및 종료 시각
```

하나의 DTO가 두 유스케이스를 모두 만족시키려면 결국 양쪽 필드의 합집합을 가지게 된다. 그러면 한쪽에서만 필요한 필드를 변경해도 다른 API의 응답 계약까지 영향을 받는다. 코드상 재사용은 늘었지만 API 간 결합도 함께 높아진다.

이번 변경에서는 엔티티를 기준으로 DTO를 만들기보다 화면과 유스케이스가 실제로 필요로 하는 데이터를 기준으로 DTO를 나눴다. `GameSummaryResponse`가 `Game`의 모든 속성을 복사하지 않는 것은 누락이 아니라 의도된 경계다.

`GameSummaryResponse`의 승자 정보는 여전히 흑 또는 백의 `PlayerSummary`와 일부 중복된다. `winnerColor`나 `winnerId`만 전달하는 방법도 가능하다. 다만 현재 프론트가 승자의 ID와 닉네임을 직접 사용하고 있고, 세 필드로 제한된 요약 객체이므로 이번에는 읽기 쉬운 계약을 유지했다. 이후 응답 크기나 계약 단순화가 더 필요해지면 승자를 색상으로 표현하는 방법을 다시 검토할 수 있다.

### 5. 수정하면서 느낀 점

이번 작업은 단순히 JSON 필드를 줄이는 작업이 아니었다. 컨트롤러의 제네릭 타입 하나를 바꾸면서 유스케이스 포트, 서비스 변환, 프론트 API 타입, 화면 상태, 다시보기 컴포넌트까지 연결되어 있었다.

이 과정에서 DTO가 계층 사이에 전달되는 데이터 묶음인 동시에 외부 클라이언트와 맺는 계약이라는 점을 다시 확인했다. 백엔드 내부에서는 필드를 하나 추가하는 것이 쉬워 보여도, 응답에 포함되는 순간 프론트가 의존할 수 있는 공개 계약이 된다. 사용하지 않는 필드도 계속 유지해야 할 것 같은 부담을 만들 수 있다.

또한 응답 최소화는 민감 정보만 숨기는 문제가 아니었다. 다음 기준을 함께 볼 필요가 있었다.

1. 이 화면에서 실제로 사용하는 값인가.
2. 클라이언트가 이미 알고 있는 값을 반복해서 보내고 있지 않은가.
3. 같은 응답 안에서 동일한 객체가 중복되고 있지 않은가.
4. 반복 개수가 많은 배열의 각 원소에 불필요한 값이 들어 있지 않은가.
5. 서로 다른 유스케이스가 편의상 같은 DTO에 결합되어 있지 않은가.

### 정리

`/games/my`는 실시간 게임용 `GameResponse` 대신 전적 목록용 `GameSummaryResponse`를 반환하도록 변경했다. 플레이어 정보도 전체 공개 프로필이 아니라 ID, 닉네임, 프로필 이미지만 가진 `PlayerSummary`로 제한했다. 프론트 역시 `GameInfo`와 `GameSummary`를 분리하여 실제 서버 응답과 타입을 맞췄다.

착수 응답에서는 방 코드, 착수자 UUID, DB 식별자, 생성 시각처럼 현재 소비되지 않는 반복 값을 제거했다.

이번 작업에서 남길 점은 다음과 같다.

1. DTO는 엔티티의 복사본이 아니라 유스케이스별 응답 계약이다.
2. 공개 가능한 정보와 해당 API에 필요한 정보는 다르다.
3. 공용 DTO 하나가 코드 중복은 줄여도 서로 다른 API의 결합을 키울 수 있다.
4. 목록과 반복 응답일수록 각 원소에 포함되는 필드를 더 엄격하게 확인해야 한다.
5. 백엔드 DTO를 변경할 때는 프론트 타입과 실제 사용처까지 함께 수정해야 계약이 일치한다.

처음에는 DTO를 여러 개 만드는 것이 중복처럼 보였지만, 이번에는 목적에 맞는 작은 DTO가 오히려 각 API의 책임과 변경 범위를 명확하게 만들었다.

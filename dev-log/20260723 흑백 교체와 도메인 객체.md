### 1. 흑백 교체 기능 이후 발견한 버그

대기방에서 방장이 참가자와 흑백을 바꿀 수 있는 기능을 추가했다. 두 참가자가 모두 입장한 상태에서 방장이 버튼을 누르면 각 `GamePlayer`의 색을 반대로 바꾸는 기능이다.

기능 자체는 정상적으로 동작했지만, 참가자가 나갔다가 새로운 참가자가 들어오는 경우까지 생각하지 못했다.

기존 참가자 생성 코드는 다음과 같이 일반 참가자의 색을 항상 `WHITE`로 지정하고 있었다.

```java
public static GamePlayer createPlayer(Room room, User user) {
    return GamePlayer.builder()
            .room(room)
            .user(user)
            .role(PlayerRole.PLAYER)
            .color(StoneColor.WHITE)
            .build();
}
```

흑백 교체 기능이 없을 때는 방장이 항상 `BLACK`, 일반 참가자가 항상 `WHITE`였기 때문에 문제가 없는 코드였다. 하지만 방장이 한 번 `WHITE`로 바뀐 뒤 기존 참가자가 나가면 상황이 달라진다. 다음 참가자도 기존 생성 규칙에 따라 `WHITE`로 들어오므로 대기방의 두 참가자가 모두 `WHITE`가 될 수 있었다.

즉 다음과 같은 순서에서 버그가 발생했다.

```text
방장 BLACK / 참가자 WHITE
        ↓ 흑백 교체
방장 WHITE / 참가자 BLACK
        ↓ 기존 참가자 퇴장
방장 WHITE
        ↓ 새로운 참가자 입장
방장 WHITE / 새 참가자 WHITE
```

기존에는 올바르던 `PLAYER는 WHITE다`라는 규칙이 흑백 교체 기능을 추가하면서 더 이상 성립하지 않게 된 것이다. 새로운 기능만 따로 보면 정상이어도, 기존 코드에 숨어 있던 전제가 함께 바뀌는지 확인해야 한다는 점을 놓쳤다.

### 2. 수정한 방향

새 참가자의 색을 무조건 `WHITE`로 지정하지 않고, 현재 방장 색의 반대편 색을 배정하도록 변경했다.

```java
GamePlayer host = loadGamePlayerPort.findByRoomIdAndRole(room.getId(), PlayerRole.HOST)
        .stream().findFirst().orElseThrow();

StoneColor joinColor =
        host.getColor() == StoneColor.BLACK ? StoneColor.WHITE : StoneColor.BLACK;

GamePlayer player = GamePlayer.createPlayer(room, user, joinColor);
```

그리고 `GamePlayer.createPlayer()`가 내부에서 색을 결정하지 않고, 호출하는 쪽에서 결정된 색을 받도록 팩토리 메서드도 수정했다.

```java
public static GamePlayer createPlayer(Room room, User user, StoneColor color) {
    return GamePlayer.builder()
            .room(room)
            .user(user)
            .role(PlayerRole.PLAYER)
            .color(color)
            .remainingSeconds(room.getTimeLimit().getSeconds())
            .build();
}
```

AI 연습 게임처럼 참가자가 반드시 `WHITE`여야 하는 경우에는 호출부에서 `StoneColor.WHITE`를 명시한다. 일반 대기방 입장은 방장의 현재 색을 기준으로 계산하고, 고정된 규칙을 가진 흐름에서는 고정 색을 전달한다. 같은 참가자 생성이라도 각 유스케이스가 색을 결정하는 이유가 다르다는 점이 코드에 드러나게 됐다.

게임 시작 로직에도 같은 가정이 남아 있었다. 기존에는 방장을 흑, 일반 참가자를 백으로 간주하여 게임을 생성했다.

```java
Game game = Game.start(room, host.getUser(), player.getUser());
```

흑백 교체 이후에는 역할과 돌 색이 일치하지 않을 수 있으므로, 실제 `GamePlayer.color`를 기준으로 흑과 백을 찾아 게임을 생성하도록 변경했다.

```java
GamePlayer black = host.getColor() == StoneColor.BLACK ? host : player;
GamePlayer white = black == host ? player : host;
Game game = Game.start(room, black.getUser(), white.getUser());
```

입장 시 색 배정만 고쳤다면 대기방 표시는 정상이어도 실제 게임이 시작되는 순간 다시 방장이 흑으로 저장되는 문제가 남았을 것이다. 기능을 수정할 때 상태가 생성되는 지점뿐 아니라 그 상태가 이후 어디에서 사용되는지도 함께 따라가야 했다.

### 3. 도메인 객체 안에서 수정하며 편했던 점

흑백 변경 자체는 서비스가 `GamePlayer`의 필드를 직접 수정하지 않고 도메인 객체의 `swapColor()`를 호출하도록 구성했다.

```java
public void swapColor() {
    this.color = this.color == StoneColor.BLACK
            ? StoneColor.WHITE
            : StoneColor.BLACK;
}
```

서비스는 누가 교체할 수 있는지, 현재 방이 대기 중인지, 참가자가 두 명인지와 같은 유스케이스의 흐름을 검증한다. 실제 플레이어의 색을 어떤 방식으로 변경하는지는 `GamePlayer`가 담당한다. 덕분에 서비스에는 BLACK이면 WHITE로, WHITE면 BLACK으로 바꾸는 상태 변경 코드가 반복되지 않았고 도메인 객체의 메서드 하나만 호출하면 됐다.

이번 수정에서 특히 편했던 부분은 `createPlayer()`의 시그니처를 변경한 점이다. 기존 메서드가 색을 내부에서 `WHITE`로 숨겨서 결정할 때는 어느 흐름이 그 전제에 의존하고 있는지 검색해야 했다. 색을 필수 인자로 바꾸자 기존 호출부가 컴파일 오류로 드러났고, 일반 입장과 AI 연습 입장이 각각 어떤 색을 사용해야 하는지 하나씩 명시할 수 있었다.

도메인 객체 안에 생성 규칙과 상태 변경 메서드가 모여 있으니 변경 범위도 명확했다.

- `GamePlayer`는 전달받은 색으로 유효한 참가자를 생성하고 자신의 색을 교체한다.
- `RoomService`는 현재 방 상태를 보고 어떤 색을 줄지 결정하며 변경된 참가자를 저장한다.
- `Game`은 역할이 아니라 실제 돌 색을 기준으로 흑과 백 사용자를 전달받는다.

이전 같았으면 서비스에서 `setColor()`를 호출하며 상태를 직접 조립했을 가능성이 크다. 그렇게 했다면 색을 바꾸는 규칙과 참가자 생성 규칙이 여러 서비스 메서드에 흩어지고, 이후 색과 관련된 조건이 추가됐을 때 다시 모든 호출부를 확인해야 했을 것이다.

도메인 객체에 모든 판단을 넣어야 한다는 의미는 아니다. 새 참가자가 방장 반대 색이어야 한다는 판단은 현재 방의 다른 참가자를 조회해야 하므로 서비스가 담당하는 것이 자연스럽다. 반면 한 플레이어의 색을 반대로 바꾸는 행위와 전달받은 색으로 참가자를 생성하는 책임은 `GamePlayer` 안에 두는 편이 응집도가 높았다.

### 정리

이번 버그는 흑백 교체 코드 자체보다 기존 코드에 숨어 있던 `방장=BLACK`, `참가자=WHITE`라는 전제 때문에 발생했다. 기능이 확장되면서 기존의 고정값은 더 이상 도메인 규칙이 아니게 됐지만, 참가자 생성과 게임 시작 로직에는 그 가정이 그대로 남아 있었다.

수정하면서 남길 점은 다음과 같다.

1. 새로운 기능이 기존 불변 조건을 깨뜨리는지 먼저 확인해야 한다.
2. 상태를 변경한 뒤에는 생성, 퇴장 후 재입장, 게임 시작처럼 그 상태를 다시 사용하는 흐름까지 따라가야 한다.
3. 팩토리 메서드의 필수 인자는 숨은 전제를 호출부에 드러내고, 컴파일러가 변경해야 할 지점을 찾게 해준다.
4. 서비스는 유스케이스를 조율하고 도메인 객체는 자신의 상태 변경을 담당하게 하면 수정 범위와 책임이 명확해진다.

작은 흑백 교체 기능이었지만, 고정값 하나가 사실은 기능이 없어서 우연히 유지되던 전제였다는 점을 확인한 작업이었다.

### 1. GitHub 공개 전 WebSocket 인가 규칙 확인중에

프로젝트를 공개하기 전 보안 관점에서 코드를 점검하면서 `JwtChannelInterceptor`를 다시 살펴봤다. 이 인터셉터는 WebSocket 연결 시 JWT를 검증하고, 이후 들어오는 STOMP 프레임의 목적지에 접근할 수 있는지도 확인한다.

기존 코드는 `SUBSCRIBE`와 `SEND`를 같은 함수로 검사하고 있었다.

```java
if (StompCommand.SUBSCRIBE.equals(accessor.getCommand())
        || StompCommand.SEND.equals(accessor.getCommand())) {
    authorizeDestination(accessor);
}
```

처음 작성할 때는 두 명령 모두 destination을 가지므로, 목적지별로 인증 사용자와 방 멤버십을 확인하면 충분하다고 생각했다. 그러나 두 명령은 같은 주소를 사용하더라도 의미가 전혀 다르다.

- `SUBSCRIBE`: 이 사용자가 해당 목적지의 메시지를 받아도 되는가
- `SEND`: 이 사용자가 해당 목적지로 메시지를 발행해도 되는가

즉, **그 방을 구독할 수 있는 사람이 그 방의 서버 이벤트까지 발행할 수 있는 것은 아니다.**

### 2. `/app`과 `/topic`?

현재 WebSocket 설정에서는 애플리케이션 목적지와 메시지 브로커 목적지를 다음과 같이 나누고 있다.

```java
registry.enableSimpleBroker("/topic", "/queue");
registry.setApplicationDestinationPrefixes("/app");
registry.setUserDestinationPrefix("/user");
```

클라이언트가 정상적으로 게임 행동을 요청할 때는 `/app/**`으로 메시지를 보낸다.

반면 `/topic/**`과 `/queue/**`는 서버가 처리 결과를 구독자에게 전달하는 브로커 목적지다. 클라이언트가 `/topic/**`으로 직접 `SEND`하면 `@MessageMapping` 컨트롤러를 거치지 않고 브로커로 전달될 수 있다.

따라서 애플리케이션 내부의 검증 코드가 아무리 잘 작성되어 있어도, 브로커 목적지로 직접 들어오는 경로가 열려 있으면 그 검증을 우회할 수 있다.

### 3. 방 멤버십 검사가 발행 권한까지 허용하고 있었다

기존 인가 함수는 `/topic/room/{roomCode}/...`에 접근할 때 방 멤버인지 확인했다.

```java
Matcher roomTopic = ROOM_TOPIC_PATTERN.matcher(destination);
if (roomTopic.matches()) {
    requireRoomMember(roomTopic.group(1), userId);
    return;
}
```

구독 인가로는 필요한 검사다. 플레이어와 관전자는 자신이 들어간 방의 착수, 상태, 채팅, 공지 이벤트를 받아야 한다.

하지만 같은 검사를 `SEND`에도 사용하면서 방 멤버라면 누구든 다음과 같은 브로커 목적지로 직접 메시지를 보낼 수 있었다.

```text
SEND /topic/room/ABC123/closed

{"message":"상대가 게임을 종료했습니다."}
```

프론트는 `/closed` 메시지를 서버가 보낸 이벤트라고 신뢰한다. 이 메시지를 받으면 종료 문구를 표시하고 3초 뒤 로비로 이동한다. 따라서 관전자를 포함한 방 멤버가 형식에 맞는 메시지를 직접 보내면 다른 사용자의 화면을 게임 종료 상태처럼 보이게 만들 수 있었다.

이 과정에서 DB의 실제 게임 상태나 전적이 변경되는 것은 아니다. 게임 서비스와 저장 로직을 거치지 않기 때문이다. 그러나 사용자는 서버가 보낸 정상 이벤트와 위조 이벤트를 구분할 수 없으므로, 진행 중인 화면을 방해하거나 상대가 게임을 종료한 것처럼 오인하게 할 수 있었다.

멤버십 검사는 “이 방의 이벤트를 읽을 수 있다”는 조건은 만족했지만, “서버를 대신하여 이 방의 이벤트를 만들 수 있다”는 권한까지 의미하지는 않았다.

### 4. 컨트롤러 검증 건너뛰기

광장 채팅의 정상적인 요청 경로는 `/app/plaza/{channelId}/chat`이다. 이 요청은 컨트롤러에서 다음 검증을 거친다.

```java
@MessageMapping("/plaza/{channelId}/chat")
public void handleChat(
        @DestinationVariable String channelId,
        @Valid @Payload ChatMessageRequest request,
        SimpMessageHeaderAccessor accessor) {
    AuthUser user = extractUser(accessor);
    if (user == null || !manager.isMember(channelId, user.id())) return;

    String nickname = user.nickname();
    ChatMessageResponse response =
            new ChatMessageResponse(nickname, null, true, request.content(), LocalDateTime.now());
    eventPublisher.publishChat(channelId, response);
}
```

여기서는 현재 광장 채널의 멤버인지 확인하고, 닉네임은 클라이언트 입력이 아니라 JWT의 인증 사용자 정보에서 가져온다. `@Valid`를 통해 빈 메시지와 200자를 넘는 메시지도 거부한다.

하지만 기존 인터셉터는 `/topic/plaza/{channelId}/...`에 대해 채널 ID 형식만 검사했다. 인증된 사용자가 형식에 맞는 채널을 골라 `/topic/plaza/{channelId}/chat`으로 직접 `SEND`하면 위 컨트롤러가 호출되지 않았다.

그 결과 다음 애플리케이션 규칙을 우회할 수 있었다.

1. 실제 채널 멤버인지 확인하는 `manager.isMember`
2. 메시지 길이와 공백을 검사하는 `@Valid`
3. 인증 사용자로부터 닉네임을 만드는 서버 권위 규칙

직접 보낸 본문을 정상 `ChatMessageResponse`처럼 구성하면 다른 사용자의 닉네임을 넣은 메시지도 구독자에게 전달할 수 있었다. 이 사례를 통해 인증된 사용자라는 사실만으로 메시지 내용까지 신뢰할 수 있는 것은 아니라는 점을 확인했다.

### 5. 구독과 전송 인가를 분리했다

수정 후에는 STOMP 명령에 따라 별도의 인가 함수를 호출한다.

```java
if (StompCommand.SUBSCRIBE.equals(accessor.getCommand())) {
    authorizeSubscribe(accessor);
} else if (StompCommand.SEND.equals(accessor.getCommand())) {
    authorizeSend(accessor);
}
```

`SUBSCRIBE`는 사용자가 받아볼 수 있는 목적지만 허용한다.

- `/topic/room/{code}/...`: 해당 방의 플레이어 또는 관전자
- `/topic/plaza/{channelId}/...`: 서버가 발급하는 광장 채널 ID 형식
- `/user/...`: 사용자별 목적지

`SEND`는 클라이언트가 요청을 전달할 수 있는 `/app/**` 목적지만 허용한다.

- `/app/game/{roomCode}/{action}`: 해당 방의 멤버
- `/app/physical/{roomCode}/{action}`: 해당 방의 실제 참가자
- `/app/plaza/{channelId}/{action}`: 서버 발급 형식의 광장 채널

목록에 없는 전송 목적지는 모두 거부한다.

```java
throw reject("허용되지 않은 전송 destination 입니다.");
```

이 방식에서는 `/topic`, `/queue`, `/user`로 향하는 클라이언트의 직접 `SEND`가 별도의 예외 목록 없이 기본적으로 차단된다. 새로운 목적지가 생기더라도 명시적으로 허용하기 전에는 사용할 수 없는 화이트리스트 방식이다.

광장 `/app/**`에서는 인터셉터가 채널 ID 형식을 확인하고, 실제 채널 존재 여부와 멤버십처럼 실시간 상태가 필요한 검증은 `PlazaSessionManager`와 컨트롤러가 담당하도록 책임을 나눴다.

### 6. 인증과 인가는 한 번으로 끝나지 않는다

처음에는 CONNECT 단계에서 JWT를 검증하고, 목적지에 방 멤버십 검사까지 적용했으므로 WebSocket 보안이 갖춰졌다고 생각했다. 그러나 이번 문제는 인증 여부가 아니라 **같은 인증 사용자에게 어떤 동작을 허용할 것인가**의 문제였다.

WebSocket 메시지에는 여러 경계가 있다.

```text
연결 가능 여부
    ↓
목적지 구독 가능 여부
    ↓
애플리케이션 요청 전송 가능 여부
    ↓
DTO 및 도메인 규칙 통과 여부
    ↓
서버 이벤트 발행
```

앞 단계의 허용이 다음 단계의 권한을 자동으로 의미하지 않는다. 특히 브로커 목적지의 이벤트를 클라이언트가 서버가 보낸 사실로 신뢰한다면, 그 목적지에 대한 발행 권한은 서버에만 있어야 한다.

또한 컨트롤러의 `@Valid`나 서비스의 멤버십 검사는 해당 컨트롤러와 서비스를 통과하는 요청에만 적용된다. 보안 점검에서는 검증 코드의 존재뿐 아니라, 그 검증을 거치지 않고 같은 결과에 도달할 수 있는 다른 경로가 있는지도 확인해야 한다.

### 7. 남은 과제

이번 문제는 실제 침해 사고가 발생해서 발견한 것이 아니라 GitHub 공개 전 정적 코드 점검에서 발견한 잠재 취약점이다. 코드상 `SEND`와 `SUBSCRIBE`를 분리하고 허용 목록을 적용했지만, 현재 `JwtChannelInterceptor` 전용 회귀 테스트는 없다.

후속 테스트에서는 최소한 다음 동작을 검증할 필요가 있다.

1. 방 멤버가 자신의 방 토픽을 `SUBSCRIBE`할 수 있다.
2. 방 외부 사용자는 해당 방 토픽을 구독할 수 없다.
3. 인증 사용자가 `/app/game`, `/app/physical`, `/app/plaza`의 허용 경로로 전송할 수 있다.
4. 방 멤버라도 `/topic/room/**`으로 직접 `SEND`할 수 없다.
5. `/topic/plaza/**`, `/queue/**`, `/user/**` 직접 전송이 거부된다.
6. 등록되지 않은 `/app/**` 경로가 기본적으로 거부된다.

단위 테스트로 인터셉터의 목적지 판정을 빠르게 확인하고, 가능하면 STOMP 클라이언트를 연결하는 통합 테스트로 브로커 직접 전송이 실제 구독자에게 도달하지 않는 것도 검증하고자 한다.

### 정리

이번 문제의 원인은 `SEND`와 `SUBSCRIBE`가 모두 destination을 가진다는 공통점만 보고 하나의 인가 규칙으로 처리한 것이었다. 하지만 구독은 메시지를 읽는 권한이고 전송은 상태 변경을 요청하거나 메시지를 발행하는 권한이므로 서로 다른 기준이 필요했다.

기존 구조에서는 방 멤버가 서버의 게임 종료 이벤트를 흉내 내거나, 광장 채팅 컨트롤러를 우회하여 멤버십·입력값·닉네임 검증을 거치지 않은 메시지를 보낼 가능성이 있었다. DB의 실제 게임 기록이 변하는 문제는 아니었지만, 클라이언트가 서버 이벤트를 신뢰한다는 점을 이용한 화면 방해와 사칭이 가능했다.

수정 후에는 구독 가능한 `/topic/**`과 전송 가능한 `/app/**`을 분리하고, 클라이언트 `SEND`는 명시한 애플리케이션 목적지만 허용하도록 변경했다.

이번 작업에서 남길 점은 다음과 같다.

1. **메시지를 받을 권한과 메시지를 발행할 권한은 다르다.**
2. **클라이언트의 요청은 `/app/**`, 서버의 브로드캐스트는 `/topic/**`이라는 경계를 코드로 강제해야 한다.**
3. **인증된 사용자도 신뢰할 수 없는 입력 주체이며, 인증 성공이 모든 목적지에 대한 권한을 의미하지 않는다.**
4. **컨트롤러 검증은 컨트롤러를 우회하는 경로가 열려 있으면 보호 수단이 되지 못한다.**
5. **인가 규칙은 허용되지 않은 경로를 하나씩 막기보다 필요한 경로만 여는 화이트리스트가 안전하다.**
6. **정적 점검으로 발견한 보안 수정도 재발을 막으려면 목적지별 회귀 테스트가 필요하다.**

STOMP의 destination을 단순한 URL 형태의 문자열로만 보았지만, 실제로는 메시지가 애플리케이션 로직으로 갈지 브로커로 바로 갈지를 결정하는 신뢰 경계였다.

### 1. JPQL @Query의 "런타임 검증" — 그 런타임은 유저의 런타임이 아니었다

#### 의문점
- 게스트 정리용 벌크 삭제를 JPQL `@Query`로 작성했는데, 프로젝트에 QueryDSL도 이미 도입돼 있어(방 검색 등) "이건 QueryDSL로 짜야 더 안전한 것 아닌가?"라는 의문이 들었다.
- JPQL은 문자열이라 컴파일 단계에서 오타가 안 잡히고 런타임 시점에서 잡히는걸로 알고있었다. 그렇다면 컴파일 안전성을 보장하는 QueryDsl이 무조건 상위호환일텐데 왜 JPQL을 많이 사용하는지 궁금했다.


#### 해당 코드
```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("DELETE FROM User u WHERE u.role = com.dopamin.omok.user.domain.UserRole.GUEST "
        + "AND u.createdAt < :cutoff")
int deleteGuestsCreatedBefore(@Param("cutoff") java.time.LocalDateTime cutoff);
```

#### 직접 검증으로 생각보다 빨리 풀린 의문 
- 일부러 User를 Users로 오타를 내보고 백엔드 서버 가동을 해보았다

#### 해당코드
```java
@Query("DELETE FROM Users u WHERE u.role = com.dopamin.omok.user.domain.UserRole.GUEST "
        + "AND u.createdAt < :cutoff")
```

#### 오류메시지
Caused by: org.hibernate.query.sqm.UnknownEntityException: Could not resolve root entity 'Users'


- UnknownEntityException이 터지며 서버 가동이 실패했다. Users라는 엔티티를 찾지 못한다는 예외이다.
- `오해한 부분`: 런타임 시점을 직접 Query를 사용하는 시점으로 생각하였다.
- `실제`: Spring Data JPA는 부팅 시점에 `@Query`의 JPQL을 미리 파싱·검증한다. 오타가 있으면 유저에게 도달하기 한참 전, 서버가 뜨는 순간 부팅에 실패하며 죽는다(fail-fast). 즉 "런타임"이 아니라 사실상 "배포 직후"에 걸린다.

#### 알게 된 것과 선택 근거
- JPQL이 컴파일에서 안 잡힌다는 사실만 보고 위험하다고 단정했는데, 부팅 검증이라는 안전망이 한 겹 더 있었다. 유저 트래픽까지 숨어드는 native 문자열 쿼리와는 위험도가 다르다.
- 결국 실무에서 JPQL과 QueryDSL을 선택하는 기준은 안전성이 아니라 쿼리의 복잡성이었다.
